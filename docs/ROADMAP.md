# dsh-member-manager 升级路线与方案

> 承接 [29-综合评估报告-v0.5.0.md](./29-综合评估报告-v0.5.0.md)：总评 ≈8.1/10，达到「可上架生产使用」，距离「成熟产品」差三件事——硬闸门、成本持久化、公开仓库发布。

## 背景与问题

v0.5.0（任务图并行 + 三个真实 bug 修复）功能面已是 DSH 生态内最完整的「可追责公司化派工」，但评估暴露了三类真实差距：

1. **闸门是纸做的**：`company.limits`（`maxConcurrentPerProvider` / `budgetTokensPerDay` / `attemptTimeoutMs` 等）当前**仅校验与展示，不拦截**——README 里自己写明「并发/预算闸门尚未强制」。用户配了预算，超了照样跑。
2. **成本会失忆**：token/请求归因是进程内计数，**重启清零**。做「成本归因」当卖点，却拿不出跨重启的可信账单。
3. **仓库没发布**：`package.json` 0.4.1 未发 0.5.0；公开仓库 `SMPcosy/dsh-member-manager` 停在 10-17 旧版名册层（★0），当前源码未推送。

不解决的话：成本卖点名不副实，预算配置形同虚设，产品力与 Star 持续倒挂。

## 目标 / 非目标

- 目标：分四个版本（v0.5.0 → v1.0.0）把差距清单清零，v1.0.0 正式发布 npm + GitHub。
- 非目标（明确不做）：不迁出 DSH 生态；不改「src/shared 纯函数内核 + src/host 运行时」的分层；不追 stardeck 式 3D 星轨视觉；不引入向量/检索类依赖（保持零运行时依赖）。

## 方案

### 方案 A（推荐）：按「发布 → 硬闸门 → 观测 → 量化成熟」四版推进

| 版本 | 主题 | 核心工作 | 验收口径 |
|---|---|---|---|
| v0.5.0 | 发布补课 | 补 `package.json` 版本号 0.5.0；`README` 顶部与英文段版本号对齐；把当前源码推到 `SMPcosy/dsh-member-manager` 覆盖旧版；npm 发 `dsh-member-manager@0.5.0`（`dsh-plugin-release` 技能走 web-auth 发布） | GitHub 主页显示 0.5.0 源码；npm `dist-tags.latest=0.5.0`；Star 破零后能进「同类主流」对比 |
| v0.6.0 | 硬闸门 + 成本持久化 | ① `company.limits` 从「校验展示」变「真拦截」：`maxConcurrentPerProvider` 派工前查活 attempt 数，满则 `E_CAPACITY` 退避；`budgetTokensPerDay` 超额拒派并告警；`attemptTimeoutMs` 超时自动 stale + 重试（配最大重试次数）；② 成本记账落 `company/ledger/`（append-only，复用 `audit.jsonl` 同款对账），重启后成本累计可恢复；③ 面板成本页改为读持久化账单 | 超预算派工被拒且可复现；重启后成本累计不减；新断言全绿 |
| v0.7.0 | 观测与自动恢复 | ① subagent 树可视化（抄 command-centre 的长处：一屏看父→子代理关系与产出）；② 失败自动重试策略（指数退避 + `maxAttempts`，取代「失败只进异常泳道等人管」）；③ 阶段机视图（抄 teamflow 的流水线展示，只读叠加不引入新状态机） | 派工失败自动退避重试 N 次后进异常；subagent 树在面板可见；测试数到 680+ |
| v1.0.0 | 量化成熟 | ① 建 DSH 生态派工基准（首层并行率 / 下游放行延迟 / 吞吐 / 故障自愈覆盖率 / 成本归因准确度），可复现可横向对比；② 面板批量操作（批量验收 / 批量取消 / 批量派工）；③ `lib/client.js` 拆分；④ 正式发布 + README/CHANGELOG/ROADMAP/评估报告随包 | 5 项分数可复现；npm 可安装；面板批量操作可用 |

### 方案 B（备选）：先补可视化、后修闸门

先把 subagent 树/阶段机视图做出来再回头补硬闸门——理由是先有「好看」才好宣传。

### 取舍

选 A。理由：闸门和成本是「卖点是否成立」的命门——现在对外讲「成本归因」「预算管控」，用户一试就发现重启清零、超了不拦，比「没有可视化」伤得多；且硬闸门改动集中在 `company-dispatcher.mjs` / `company-scheduler.mjs` 已知路径，风险低、收益立竿见影。B 的唯一好处（先有可炫的界面）在「卖点名不副实」的现状下不成立——先让卖点真的成立，再谈美观。

## 风险

| 风险 | 概率 | 影响 | 应对 |
| --- | --- | --- | --- |
| 预算闸门误杀长任务（单任务超日预算） | 中 | 合法任务被拒 | 预算只做「软拦截 + 告警」，超时可走人工 `company_admin` 放行，不做硬杀 |
| 成本持久化与审计双账本不一致 | 中 | 对不上账 | 统一走 `ledger/` 单账本，`audit.jsonl` 只记事件、成本数由 ledger 重放得出 |
| 自动重试放大失败（坏任务重试 N 次烧 token） | 中 | 成本翻倍 | 重试上限 + 指数退避 + 重试前写 `routeError`，同一失败原因连续 N 次进异常停手 |
| 竞品同期迭代 | 中 | 差距被拉开 | 每月竞品 `gh` 快照进共享库台账 |

## 验收标准

- [ ] v0.5.0：npm `dist-tags.latest=0.5.0`；GitHub 主页是 0.5.0 源码；`README` 无旧版本号残留
- [ ] v0.6.0：超预算派工被拒有可复现断言；重启后成本累计不减；并发满员退避不误杀
- [ ] v0.7.0：派工失败自动退避重试后进异常；subagent 树面板可见；测试数 ≥680
- [ ] v1.0.0：5 项基准分数可复现；npm 可安装；README/CHANGELOG/ROADMAP/评估报告随包
