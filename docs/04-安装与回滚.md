## ⭐ 真正的根因（已本地复现，务必先读这一节）

插件"装了但没生效"的**实际原因**只有一个，且可以在本地精确复现：

```js
// ❌ 致命写法
export function apply(ctx) {
  const config = (typeof ctx.config === "object" && ctx.config) || {};   // 抛错！
```

**Cordis 把插件配置作为 `apply` 的第二个参数传入** —— 官方 `dsh-web-app`、`dshmarket`、
`dsh-experimental-tool-agent-team` 的签名全部是 `apply(ctx, config)`。
而 `config` **不在 `inject` 列表里**，在 cordis 的 Context 上访问**未声明的属性会抛错**，
于是 `apply` 在第一条语句就中断：模块加载了、`apply` 进入了，然后工具、路由、后续一切都没发生。

**复现方式**（已固化为回归测试）——用一个"访问未声明属性即抛错"的 Proxy 当 ctx：

| 版本 | 结果 |
|------|------|
| 修复前（读 `ctx.config`） | **0 个工具、0 条路由**（与生产现象完全一致） |
| 修复后（用第二个参数，兜底包 try） | **9 个工具、3 条路由** ✅ |

**为什么单元测试没抓到**：测试替身是普通对象，`ctx.config` 读得到；真实 cordis Context 是 Proxy，
读未声明属性会抛。**测试替身必须模拟这个语义**，否则这类 bug 100% 漏网。

**正确写法**：
```js
export function apply(ctx, config) {
  let cfg = {};
  try { if (config && typeof config === "object") cfg = config; } catch { cfg = {}; }
  // 若为兼容其他宿主而读 ctx.config，必须包在 try 里 —— 这次访问本身就是抛错点
  try { if (Object.keys(cfg).length === 0 && ctx.config) cfg = ctx.config; } catch {}
}
```

### 同时做的另外两处改动（合理，但**未单独隔离验证**是否必要）

诚实说明：下面两项是在排查过程中一并做的，属于消除真实歧义的好实践，
但**没有做 A/B 隔离实验**证明它们各自是必需的 —— 真正被复现确认的根因只有上面那条 `ctx.config`。

1. **激活入口从 bundle 层移到 profile 的 `cordis.patch.yml`（用户 patch 层）** —— 依据是 CLI 的
   `error: profile "desktop" is managed exclusively by the Electron application`，以及
   `dsh.profile.bundles` 受应用激活闸门（`HostPluginActivation`）管辖、市场日志显示激活由宿主完成。
2. **insert 行的 `name` 用绝对路径**（loader 会转成 `file:///...` URL），避免依赖 launcher 基于
   「已激活 bundle」构建的 runtime resolution 表。

## desktop profile 由 Electron 应用独占管辖（实测）

```powershell
PS> dsh --profile desktop --dump-config
error: profile "desktop" is managed exclusively by the Electron application
```

**实证**：

1. **CLI 的 `dsh plugin --profile desktop add link:<路径>` 只完成 pnpm 安装 + 写入 `dsh.profile.bundles`，但并不等于"已激活"。**
2. 应用对有 **bundle 层** 施加了自己的激活闸门（`HostPluginActivation`，见 `dshmarket` 的 `desktopProfiles.pluginActivation` 与客户端 `activations[name].state === "restart"`）。
3. 市场日志 `profiles\desktop\.dsh-market\log.ndjson` 里，成功安装的插件记录形如
   `"@liustack/modlens: the host's own replay activated it; adopted instead of mounting a second copy"` —— **激活由宿主完成**；而本插件的 CLI 安装在该日志里**没有任何记录**。
4. 实证：2026-10-15 05:54 完整重启后（进程全部换新），`GET /api/dsh-member-manager/health` 仍返回 **401**，而同为第三方插件的 `dsh-skills-manager` 路由返回 **405** ⇒ **bundle 层条目没有被激活**。

**解决办法（已实施）**：把条目改挂到 **profile 自己的 `cordis.patch.yml`（用户 patch 层）**。
`cordis.yml` 顶部注释写明合成顺序是 `bundles → cordis.patch.yml → --patch overlays`，用户层**无条件应用**（该层里已有的 `agent-default-model`、`llm-pi-ai`、`permission` 等条目都确实生效）。

## ⚠️ BOM 陷阱（真实踩到，差点弄坏 profile）

**PowerShell 的 `Set-Content -Encoding UTF8` 会写入 BOM**（`EF BB BF`），而 DSH 的 `readProfileManifest` 对文件内容直接 `JSON.parse` ⇒ **带 BOM 的 `package.json` 会让整个 profile 加载失败**：

```
SyntaxError: Unexpected token '', "{ "name"... is not valid JSON
    at readProfileManifest (.../dsh-app-boot/lib/index.js:835)
```

**本次实际发生过**：用 PowerShell 改写 profile 的 `package.json`、`cordis.patch.yml` 以及插件的 `package.json` 后，三个文件都带上了 BOM。已全部去除，并校验首字节为 `7b`（`{`）。

**规则**：改这些 JSON/YAML 文件时，**必须用无 BOM 的 UTF-8**（`edit`/`write` 工具，或 Node 的 `fs.writeFileSync(path, text)`），不要用 PowerShell 的 `Set-Content -Encoding UTF8`。

## 无需重启即可验证合成结果（本次排查用的技巧）

CLI 拒绝 `--profile desktop`，但**拒绝的是名字，不是内容**。把 profile 复制成一个别的名字即可用**真实 loader** 校验：

```powershell
$P = "C:\Users\Ren\.dsh\profiles\desktop"; $C = "C:\Users\Ren\.dsh\profiles\clonediag"
New-Item -ItemType Directory -Force $C | Out-Null
foreach ($f in 'package.json','cordis.yml','cordis.patch.yml','pnpm-workspace.yaml','pnpm-lock.yaml') { Copy-Item "$P\$f" "$C\$f" -Force }
New-Item -ItemType Junction -Path "$C\node_modules" -Target "$P\node_modules"
dsh --profile clonediag --dump-config      # 搜索目标 id，确认出现且来源层正确
cmd /c rmdir "$C\node_modules"; Remove-Item $C -Recurse -Force   # 清理（先删 junction 再删目录！）
```

**注意**：必须先 `rmdir` 掉 junction 再删目录，否则可能误删真实 `node_modules`。

## 回滚

**注意**：因为激活入口在用户 patch 层，**只跑 CLI remove 不够**，必须同时删掉 `cordis.patch.yml` 里的 `insert` 行。

### 方式 A：两步清理

```powershell
$P = "C:\Users\Ren\.dsh\profiles\desktop"
# 1) 从用户 patch 层删掉本插件的 insert 行（手工编辑 cordis.patch.yml：
#    删除末尾 "# === 成员管理插件（本地开发）===" 注释块及随后的 - insert: ... 两行）
# 2) 卸载模块
dsh plugin --profile desktop remove dsh-member-manager
# 3) 重启 DSH
```

> 编辑 `cordis.patch.yml` 时**不要用 PowerShell 的 `Set-Content -Encoding UTF8`**（会加 BOM，见上文陷阱）；用编辑工具或 Node 写入无 BOM 的 UTF-8。
> 该文件**不可留空**——不用时应写成 `[]`（空文件会导致启动失败）。

### 方式 B：从备份恢复（推荐，最省事）

```powershell
$P = "C:\Users\Ren\.dsh\profiles\desktop"
$B = "C:\Users\Ren\Documents\deepseek-harness\default-workspace\dsh-member-manager\backup"
# 恢复到"改 patch 层之前"的状态
Copy-Item "$B\cordis.patch.yml.bak2" "$P\cordis.patch.yml" -Force
Copy-Item "$B\package.json.bak2"     "$P\package.json"     -Force
# 若还要彻底移除依赖，再用 CLI remove + pnpm install
Remove-Item "$P\node_modules\dsh-member-manager" -Force -Recurse
# 重启 DSH
```

插件数据独立存放在 `~\.dsh\storages\member-manager\`：

## 兼容性声明策略

**不要声明 `@deepseek-ai/dsh-*` 的 `peerDependencies`**，除非确实 import 了它们。

原因（已由源码与实测双重确认）：
- `evaluatePluginCompatibility` 会拿每个 `@deepseek-ai/dsh*` peer range 去匹配运行时版本 `0.2.0-rc.2`；
- semver 里 `"*"` **不匹配预发布版本**，所以 `"@deepseek-ai/dsh-tools": "*"` 会被判为不兼容而**拒绝安装**；
- 本插件 Host 端刻意不 import 任何官方包（工具定义走普通对象 + `ctx` 服务注入），客户端只 `require("react")`（平台模块表提供），因此**无需任何 peer 声明**；
- `dsh.compatibility` 字段在当前实现里**没有读取点**，不要依赖它。

## v0.2.0 更新与回滚（分阶段更新）

> 原则：**绝不在 DSH 运行中替换插件目录**。0.2.0 的「自动更新」只负责把新版下载到 staging 并记 pending，真正的替换发生在下次启动**之前**。

### 四段式流程

| 阶段 | 面板/工具 | 做了什么 | 风险 |
| --- | --- | --- | --- |
| check | 维护页「检查更新」/ `member_update{action:"check"}` | GET registry 元数据，比较版本 | 只读网络 |
| stage | 「暂存更新」/ `action:"stage"`；或配置 `update.checkOnBoot+autoStage` 自动暂存 | 下载 tgz → 校验包名/版本/`integrity` → 解到 `{dataDir}/updates/<version>/` → 写 `pending.json` | 只写数据目录 |
| apply | **退出 DSH 后**在终端运行 `node scripts/apply-pending.mjs --data-dir ... --install-dir ... --yes`；面板「应用」按钮会拒绝并给出命令 | 先备份旧目录，再覆盖；失败自动恢复 | 会改安装目录 |
| rollback | 「回滚上次更新」/ `action:"rollback"` | 用 `updates/backups/<旧版本>/` 覆盖回去 | 会改安装目录 |

### 被拒绝的情况（会返回明确错误码，不产生副作用）

- `NEEDS_OFFLINE_APPLY`：面板在线 apply 被设计性拒绝（默认行为）。这是安全约束，不是故障；按返回的 `applyCommand` 在 DSH 退出后执行即可。
- `JUNCTION_INSTALL`：安装位是 `link:`/junction（当前 desktop profile 就是这种）。这是**预期行为**——用 link 安装时请直接 `git pull` 或重新 `npm install`，不要用插件自更新。
- `NO_PENDING` / `STAGED_MISSING` / `STAGED_INVALID`：没有暂存或暂存内容不合法。
- `NAME_MISMATCH`：tgz 里的包名不是 `dsh-member-manager`。
- `INSTALL_MISSING`：安装目录不存在（先正常安装一次）。

### 手动回滚（任何时候都可用）

```powershell
# 1) 名册回滚（0.2.0 新增：每次写入后自动备份）
# 面板「维护 → 备份 → 恢复」，或：
#   member_backup { action: "list" }
#   member_backup { action: "restore", file: "registry-20261019T....json" }
# 恢复前会自动先备份当前名册（reason=pre-restore）

# 2) 插件版本回滚：退出 DSH → 删除插件目录 → 安装旧版本 → 启动
```

### 升级会丢组织架构吗？

不会。名册在 `{dataDir}/registry.json`，与插件代码目录分离；0.2.0 起每次写入名册后 1.5s 内自动快照、启动时再补一份，备份在 `{dataDir}/backups/`，按「最近 20 份 + 最近 7 天每天一份」轮转。即使误删 `registry.json`，也能从备份恢复。

### 仍然必须重启才能生效的改动

见上表「迭代时的注意事项」：Host/客户端代码改动都需要重启 DSH；0.2.0 自身也不例外。
