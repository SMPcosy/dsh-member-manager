# dsh-plugin-member-manager · 验证计划

> 原则：**每一条能力都要有可复现的验证动作与可观察的证据**，不接受「代码写完了就算完成」。
> 环境：DSH desktop profile，Web GUI http://127.0.0.1:19387

## 0. 验证前置

| 项 | 内容 |
|----|------|
| 被测对象 | 本地插件 `dsh-plugin-member-manager`，装入 `C:\Users\Ren\.dsh\profiles\desktop` |
| 基线备份 | 改动 profile 前，先备份 `package.json`、`cordis.patch.yml`、`pnpm-workspace.yaml` 到插件项目的 `backup\` |
| 回滚手段 | 恢复上述三个备份文件 + 重启 DSH；registry 数据文件删除即回到初始态 |
| 当前团队成员快照 | Lead + `kb-organizer`、`data-fact-checker`（已停用）、`data-organizer`、`data-verifier`（在用） |

## 1. 装载验证（P0）

| # | 验证动作 | 期望证据 |
|---|----------|----------|
| 1.1 | 插件条目加入 profile 后启动/重载 DSH | 启动日志无插件报错；插件出现在设置页的插件清单里 |
| 1.2 | 检查插件注册的 tool 是否可见 | 宿主端能列出 `member_*` 工具（或插件自报注册成功） |
| 1.3 | 故意写错一处配置，确认能看出失败 | 日志有明确报错，且不影响 DSH 其余功能 → 证明验证方法有效（**阴性对照**） |

## 2. 数据层验证（P0）

| # | 验证动作 | 期望证据 |
|---|----------|----------|
| 2.1 | 首次运行 | 生成 registry 数据文件，`version=1`，结构符合设计 |
| 2.2 | 重启 DSH | 数据仍在（持久化生效） |
| 2.3 | 手写一个非法 JSON 进数据文件后启动 | 插件不崩溃、有告警、能自愈或给出明确错误 |
| 2.4 | 名册里有核心已不存在的 target | 标记为「孤儿」，不自动删除 |

## 3. 功能验证（每项都要「改完能读到」）

| # | 能力 | 验证动作 | 期望证据 |
|---|------|----------|----------|
| 3.1 | 组织架构 | 建 2 个小组、把成员分配到组 | `member_list` 输出两级树；UI 面板同样显示 |
| 3.2 | 添加成员 | 登记一个现有 target；再试登记不存在的 target | 前者成功入库；后者被拒并给出原因 |
| 3.3 | 重命名成员 | 把 `data-organizer` 的显示名设为「数据整理员」 | 名册与 UI 均显示中文名；**核心 `list_agents` 的 target 不变**（关键断言） |
| 3.4 | 岗位职责 | 设 title=「知识库整理员」+ 3 条 duties | 读回一致，UI 展示 |
| 3.5 | 技能赋予 | 给成员挂 `file-processing-master` 与一个自定义标签 | 读回一致；原生 skill 名可校验存在性 |
| 3.6 | 删除（软） | 停用某成员 | 默认组织架构视图不再显示；「已停用」里可见；可恢复；**核心团队不受影响** |
| 3.7 | 边界 | 重复登记同一 target；重命名成空字符串；超长显示名；给不存在的小组分配成员 | 均被拒绝并有明确错误信息 |

## 5. 回归验证（P0）—— 证明「没把 DSH 弄坏」

| # | 验证动作 | 期望证据 |
|---|----------|----------|
| 5.1 | 插件启用状态下，正常跑一次团队协作（`send_message` 给某成员、`team_task_list`） | 原有团队功能完全正常 |
| 5.2 | 对比插件启用前后的 profile 文件 diff | 只多了本插件相关条目，无意外改动 |
| 5.3 | 卸载插件（移除条目 + 重启） | DSH 恢复正常，无残留报错 |

## 7. 验收定义

**只有同时满足以下三条才算完成：**
1. 第 1~5 节全部验证项有实际执行记录与证据，无未解释的失败项；
2. 用户能在 GUI 里完成「建组 → 加人 → 改名 → 设岗位 → 赋技能 → 停用 → 恢复」全流程；
3. 第 5 节回归验证通过，证明 DSH 原有团队功能未被破坏。
