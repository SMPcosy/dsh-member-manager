### 更新（2026-10-15 05:54 完整重启之后）：真实根因已查明并修复

用户已完成一次**完整重启**（主进程 05:34:06 → 05:54:33 全部换新），但插件**仍未激活**。逐层排查结论：

| 环节 | 结果 | 证据 |
|------|------|------|
| profile 合成 | ✅ 正确 | 克隆 profile + `dsh --profile <克隆> --dump-config` ⇒ 条目出现、来源层正确 |
| 模块解析 | ✅ 正确 | 从 profile 发起 `require.resolve("dsh-plugin-member-manager")` 成功 |
| 模块导入 / `apply` | ✅ 正确 | 隔离环境实测：导入成功，`apply` 注册 12 个工具无报错 |
| **激活** | ❌ **bundle 层条目不生效** | `/health` → 401，而同为第三方的 `dsh-skills-manager` 路由 → 405 |
| **根因** | **desktop profile 由 Electron 应用独占管辖** | CLI 亲口报错：`profile "desktop" is managed exclusively by the Electron application`；市场日志显示激活由宿主完成（`"...the host's own replay activated it"`），而本插件的 CLI 安装在该日志里**无任何记录** |

**已实施的修复**：把条目从 `dsh.profile.bundles`（受应用激活闸门管辖）改挂到 **profile 自己的 `cordis.patch.yml`（用户 patch 层，无条件应用）**；并用真实 loader 在克隆 profile 上验证：条目**恰好出现一次**、来源标注为该 patch 文件、合成零告警（除一条既有的 whale-pet 无关告警）。详见 `docs/04-安装与回滚.md`。

**顺带排掉一个严重隐患**：排查中发现 PowerShell 的 `Set-Content -Encoding UTF8` 给 profile 的 `package.json`、`cordis.patch.yml` 以及插件 `package.json` **写入了 BOM**，而 loader 对文件内容直接 `JSON.parse` —— 带 BOM 会让**整个 profile 加载失败**。已全部去除并全盘复查（21 个文件 0 残留）。若非用「克隆 + dump-config」校验，这个 BOM 会在下一次启动时直接弄坏用户的 DSH。

⇒ **现在只差一次重启**。重启后按 `docs/04-安装与回滚.md` 的「安装后验证清单」执行（第 0 步：`/health` 应返回 200）。

**一个不可用的探针（诚实记录）**：`/plugins/<包名>/client` 系列路径即使对**已加载**的插件也返回 404（对 `dshmarket` / `dsh-whale-widget` / `@michengai/dsh-skills-manager` 三个已生效插件同样 404）。因此该路径受鉴权保护、**无法**用作我这侧的客户端半侧探针；客户端是否生效只能由用户在界面里确认。

## 自诊断工具（本轮新增，用于重启后快速定位）

新增第 9 个工具 `member_diagnose`，一次调用即可回答「到底哪一层没起来」：

| 检查项 | 判据 | 失败含义 |
|--------|------|----------|
| `registryDirWritable` | 写探针文件实测 | 名册无法持久化（权限/DSH_HOME 问题） |
| `registryFileExists` | 信息项，**不存在不算失败** | 首次运行本来就还没有文件 |
| `registryLoads` | 结构校验 + 告警 | 数据文件损坏（已自动隔离） |
| `coreTeamService` | `ctx.get("agentTeams")` 是否非空 | 核心成员列表不可用（工具与面板其余功能仍正常） |
| `webPanelsRoutes` | 路由是否成功注册 | Web 面板打不开（工具不受影响） |

并返回 `failed[]` 与可操作 `hints[]`；**孤儿成员只作为提示，不会让整体 `ok=false`**。已由 6 个测试覆盖（含目录不可写、路由抛错、核心缺失、孤儿提示）。

## 尚未验证的风险点（诚实列出）

1. 重启后插件是否真能被加载 —— 未验证（前置校验 23/23 通过，但那是静态校验）。重启后先跑 `member_diagnose`，它会直接指出是宿主层、核心服务层还是面板层的问题。
2. 三个插槽名（`settings.section` / `sidebar.panellist` / `main`）是从真实源码里「出现过」的集合中选取的，**不是权威全集**。已做韧性处理：任一插槽失败只丢该入口并告警，不会让插件加载失败。仍需真机确认哪些入口实际出现。
3. `sidebar.panellist` 组件除 `label` 外的 props 形状未证实（失败也只会表现为侧栏图标不显示，不影响功能）。
4. 宿主端读核心成员依赖服务名 `agentTeams`（证据充分：官方 `dsh-experimental-tool-agent-team` 的 `inject` 列表里就是这个名字）。**读取逻辑与全部降级分支已用替身测过**，但真实服务对象未接入验证；服务名若不符只会走 `coreAvailable=false` 降级（不崩），且 `member_diagnose` 会明确报出。
