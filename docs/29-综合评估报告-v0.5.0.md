## 2. 代码质量

### 2.1 结构（好）

分层干净，职责边界清楚：

| 层 | 文件 | 职责 | 行数 |
| --- | --- | --- | --- |
| 纯函数内核 | `src/shared/*.mjs`（14 个） | 组织/账本/路由/配置/计划/存储，全部无副作用 | 3,931 |
| 运行时 | `src/host/*.mjs`（7 个） | 调度/派工/兼容/员工/更新/工作流，接宿主服务 | 4,980 |
| 插件入口 | `lib/index.js` + `lib/client.js` | 工具注册 / HTTP 路由 / 面板 UI | 9,902 |

`src/shared` 是纯函数内核——`createOrder` / `isOrderReady` / `normalizePlan`（Kahn 分层）等全部可脱离宿主单测，这是 655 项测试能覆盖到「图环检测 / 忙碌门禁 / 调度间隔」这类边界的原因。

### 2.2 测试保障（9.0 / 10）

- 33 个测试文件、13,213 行断言，覆盖名册层 + 公司化运行时 + 面板 bundle + 迁移脚本。
- 关键风险路径全部有回归测试：`company-order-lossless`（undefined 键）、`company-plan`（环/重 key/超 50）、`company-scheduler-interval`（轮询间隔）、`company-employee-busy`（忙碌门禁）、`company-dispatch-v04`（派工闭环 + 孤儿回收）。
- 全量 `node --test "test/*.test.mjs"` → **655 passed / 0 failed**。

### 2.3 真实教训（这段比分数值钱）

过去三轮迭代里，每个 bug 都是「真机才暴露、假 harness 测不出」：

1. **调度间隔被错设成 1 小时**：`createScheduler({ intervalMs: config.limits.staleAttemptMs })` 把「僵死阈值 3600000」当轮询间隔，于是 DAG 第二层解锁、改派重试全要等一小时——下单时的 `kick(0)` 让第一层立刻派出，看图会误以为「并行成功」。修法是拆出独立的 `schedulerIntervalMs`（默认 5000），并让 `health.scheduler.intervalMs` 从调度器实例读真值，测试才算真验到传递链。
2. **同一员工被连派两单顶掉上一个会话**：`withLedger()` 每次从 store 重载公司状态，派工路径只 `saveLedger` 不 `saveCompany`，刚标 `working` 的人在下一单看来又 `idle`，`per_task` 下第二次派工把第一单会话直接 `end`——第一个 attempt 永远收不到 report。修法是派工后补 `saveCompany` + 新增 `E_EMPLOYEE_BUSY` 忙碌门禁。
3. **员工的白名单误导**：`company-employees.mjs` 的 `toolList` 提示词只列 `company_*`，员工读完以为「没文件没 shell」，历史上 E0001/E0023/E0017 三次停工求助都由这段文案引起——而代码里非 `company_` 工具本就直接放行。

**教训：公司员工的 `company_report` 不等于落盘证据，必须自己验；真机重启核查是必需品，不是加分项。**

### 2.4 可维护性（8.0 / 10）

- 加分：零运行时依赖（只用 Node 内置 + 宿主注入）；`docs/` 00–28 覆盖需求、契约、审阅、教程；`scripts/` 有迁移/回滚/切换/验证四件套。
- 减分：`lib/client.js` 9,902 行、`src/host/company-runtime.mjs` 2,069 行偏大（功能堆叠但未拆模块）；版本号滞后（`package.json` 0.4.1 vs `CHANGELOG` 0.5.0 未发布 vs `README` 顶部 0.4.1、英文段还写 0.3.0）。

## 3. 功能面

### 3.1 一句话定位

**把「临时拉一个 AI 干活」，变成「一家有档案、有账本、能追责的公司」。**

### 3.2 功能清单（v0.5.0）

- 组织：部门 `D01…`、员工工号 `E0001…`、M/P 双通道等级（可并存）、编制、接单范围、借调策略、名册覆盖层（显示名/岗位/职责/技能/模型覆盖）。
- 派工闭环：`order → 五级路由回退 → attempt → accept → report → review`；`attemptId` 防串单、重派先吊销、派工失败回滚、重启冷恢复。
- 任务图并行（v0.5.0）：`company_plan` 一次提交 DAG，Kahn 分层，无依赖同层并行、下游等上游 `done` 自动放行；`company_status({group})` 整批进度。
- 工作网看板：五泳道 + KPI + 调度器状态 + 部门产能条 + 拓扑；异常记录区 + 重启进度按钮。
- 成本 & 审计：token/请求按员工/部门/工单归因（`/company/costs`）；`audit.jsonl` append-only 重放对账。
- 故障自愈：冷恢复 / 孤儿回收 / 失败单可取消 / 忙碌门禁 / 调度间隔修复。
- 线隔离：OWNER 14 / 经理 12 / 员工 5 / 窗口 5，越权 `E_TOOL_LINE`。

### 4.1 结论

- **功能面最全、唯一「可追责」**：本项目是 DSH 生态内唯一同时具备「组织持久化 + 派工闭环 + DAG 并行 + 审计账本 + 成本归因 + 故障自愈」六项的插件。竞品各占一到两项（dag-orchestrator 有 DAG 无组织、teamflow 有阶段机无账本、command-centre 有树可视化但纯只读）。
- **Star 归零是发布问题，不是产品问题**：公开仓库 `SMPcosy/dsh-member-manager` 停在 10-17 旧版名册层（★0），当前 0.5.0 源码未推送。对比 agent-workflow ★311 只做「只读可视化」、dsh-bot ★28 只做「临时团队」，产品力差距与 Star 完全倒挂。
- **生态外 edict ★17,039 是唯一「同构」参照**：三省六部制（12 agent + 制度性审核 + 看板）思想与本案「部门 + 工号 + 派工 + 审计」同源，但 edict 非 DSH 插件、无成本归因、无 DAG。本案的差异化不在「组织」而在「账本 + 成本 + 故障自愈」。

## 7. 已修的真实坑（v0.3.0 → v0.5.0）

- P0：消息无唯一 id（`undefined` 撞内核去重崩）；停工伪造 turn（`reason:null` 崩 subagentTiming 投影）—— v0.4.1
- P0：`company_order` 返回 `value is not lossless JSON`（undefined 键），但单实际建成—— `stripUndefined` + 出口兜底
- P1：异常泳道死锁（`cancelOrder` 拒 failed→cancelled，账本却允许）；终态订单孤儿 attempt 永不回收
- P1：调度间隔 1 小时；订单状态变化不推调度；同一员工连派两单顶会话

## 8. 最大卖点（对外一句话能说清）

1. **能追责**：每笔派工有 `attemptId` + `audit.jsonl`，谁干的、干到第几次、被吊销过没有、花了多少 token，重启后都对得上——这是「编排类插件」（只有可视化/只有 DAG）和「公司类插件」（只有组织）都没有的。
2. **故障自愈是验证过的，不是宣称的**：冷恢复 / 孤儿回收 / 失败可取消 / 忙碌门禁，每条都有对应测试 + 真机重启日志，可直接给用户看 `audit.jsonl` 时间线。
3. **组织持久化**：部门 + 工号 + M/P 双通道等级 + 名册覆盖层，重启后重建所有权链，临时拉人变成长期建制。
4. **DAG 并行**（v0.5.0）：一次提交任务图，同层并行、下游等上游自动放行，补上「一张图里哪些能同时干」的结构。
5. **零运行时依赖**：只吃 Node 内置 + 宿主注入，装完即用，不拖一堆 native 依赖。

诚实边界（对外也要说，避免过度承诺）：并发/预算闸门当前只校验不强制；成本为进程内计数重启清零；无阶段机、无 subagent 树可视化。
