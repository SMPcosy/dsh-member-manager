## 0. 基本原则

1. **单包自洽**：所有新能力并入 `dsh-member-manager@0.3.0`，不依赖第三方插件；只用宿主 `ctx.agents` / `ctx.subagents` / `ctx.tools` / `ctx.llm` / `ctx.systemPrompt` / `ctx.webServer`。
2. **不复用原生团队层**：不调用 `ctx.agentTeams` 做公司运行时（名册面板仍可读它做兼容展示）。
3. **纯函数优先**：`src/shared/company-*.mjs` 零 DSH 依赖，可被 `node --test` 直接导入；宿主副作用只出现在 `src/host/company-*.mjs`。
4. **数据落盘**：`dataDir/company/company.json` + `dataDir/company/ledger/*.jsonl` + `dataDir/company/audit.jsonl`；`dataDir` 默认仍为 `~/.dsh/storages/member-manager`（数据连续性）。公司状态**不得**写进任何 workspace。
5. **失败降级**：任何运行时错误只 warn，不得阻塞插件 mount / 宿主启动。

### 1.4 冻结测试冲突裁决（Lead，2026-10-20）

`test/company-ledger.test.mjs` 原始版本内部矛盾，已在 Lead 裁决后修正一处测试写法（**断言意图不变**）：

- 「状态机：非法转移抛出 LedgerError」要求 `queued -> done`、`routed -> done` 都抛 `LedgerError`；
- 「isOrderReady 基于 deps 完成状态」原先用 `transitionOrder(depId, "done")`（dep 为 `queued`）把依赖置为完成，隐含允许 `queued -> done`。

**裁决：显式状态机用例优先，状态机严格化。** 唯一合法进入 `done` 的路径是 `running -> done`。`isOrderReady` 用例已改为 `routed -> running -> done`，其余断言不动。

因此 `company-ledger.mjs` 的 `STATE_MACHINE` 必须满足：

| from | to（合法） |
| --- | --- |
| queued | routed, running, cancelled |
| routed | running, cancelled |
| running | done, failed, lost, routed |
| failed | queued |
| done / cancelled / lost | （终态，无可达） |

补充：`running` 转移前仍需校验 `deps` 全部 `done`（现有实现保留）。

### 1.5 运行时动作在严格状态机下的合法链路（Lead 裁决，2026-10-20 第二轮）

严格状态机带来一个必然结论：**任何"完成任务/取消任务"的动作都不能跳步**。运行时（`src/host/company-*.mjs`）必须按下表实现，遇到非法边返回结构化错误 `{ ok:false, code:"E_INVALID_TRANSITION" }`，不得 throw 到宿主：

| 运行时动作 | 合法链路 |
| --- | --- |
| `review(pass)` | 只接受 `running` 单：`running → done` |
| `review(reject)` | 只接受 `running` 单：`running → failed`，再 `failed → queued`（重新入队，等待重派） |
| `cancelOrder` | `running` 单：`invalidateAttempt`（作废 attempt）+ `running → failed → queued → cancelled` 三步链；`routed` 单：`routed → cancelled`；`queued` 单：`queued → cancelled` |
| `completeOrder` | 只允许 `running → done` |
| 派工（`assignAndWake`） | 必须先把订单 `queued → routed`，再在同一业务动作里 `routed → running`；**员工 selection 与"置 working"必须与 attempt 创建在同一个 `store.withLock` 临界区**，避免两个锁之间同一员工被并发双派 |

`routeOrder` 只负责"按规则表决定部门"，不选人；选人 + 置 working 全部在 `assignAndWake` 的锁内完成。

### 2.1 统一入口 `company-runtime.mjs`

```js
export function createCompanyRuntime(ctx, { dataDir, config, logger } = {})
// -> {
//   tools: ToolDefinition[]          // 全部 company_* 工具（原生 JSON Schema parameters，与现有工具同风格）
//   routes: Array<{ method: "GET"|"POST", path: string, handler(req,res,url) }>
//                                    // path 以 /company 开头，由 lib/index.js 拼到 API_PREFIX 下
//   boot(): Promise<{ ok, warnings: string[] }>   // 幂等；内部自行 setTimeout 启动，resolve 时已完成同步准备
//   shutdown(): Promise<void>        // 停派工 -> whenIdle(带超时) -> cancel(keepInbox) -> drainChildren -> 写审计
//   view(): object                   // 供 GET /company 与 company_status 复用
// }
```

- `ctx` 缺 `agents`/`subagents` 时：所有工具仍注册但返回 `{ ok:false, code:"E_NO_AGENTS" }`，`boot()` 返回 warnings，不抛。
- 施工顺序建议：`company-compat.mjs`（宿主事件/`UserMessage.source`/能力探测）→ `company-employees.mjs`（员工 CRUD + 会话启停）→ `company-dispatcher.mjs`（order→attempt→唤醒→回报→验收收尾）→ `company-scheduler.mjs`（事件驱动 + 定时巡检）→ `company-runtime.mjs`（组装）。
- 事件订阅必须在 `ctx.effect()` 里，dispose 时全部解除。
- 唤醒统一走 `company-compat.wakeAgent(...)`：`ctx.agents.get(id)`（同步）→ 无活 Agent 则 `ctx.agents.resume({ resumeSessionId, parentAgent })` → `agent.followup(userMessage)`；**不新建会话**（新建只走 `employee.ensureSession` 的 `startActivation` 分支）。`UserMessage.source` 用 `{ kind: "company-runtime" }`（见 docs/12 实测）。

1. 员工子 Agent 创建时 `agentCtx.tools.restrict(allow 白名单)`（只过滤继承层，挡不住自有层）；
2. `agentCtx.tools.guard((exec) => reason | undefined)` 同步硬拒（**放行必须 return undefined**，返回任何字符串=拒绝），用 `exec.agent.session.id` 反查 `runtime.sessionTools`；
3. 工具执行体（`wrapExecute`）再次按 `exec.agent.session.id` 反查，越权返回 `{ ok:false, code:"E_TOOL_LINE" }`。

### 2.3 所有权模型（2026-10-20 晚定稿，B2 阻断项的对策）

`drainChildren` 只接受**直接子级**（dsh-subagent/lib/index.js:1372-1383 硬校验，且不递归），因此采用单一 owner 模型：

- **owner = 根级 runtime agent**：首次 `ctx.agents.create({ sessionId, agentOptions })`（不传 `parentAgent` → 根级，返回 `AgentHandle`）；DSH 重启后 `ctx.agents.resume({ resumeSessionId })` 恢复。`ownerSessionId` 记入审计流（`audit.jsonl` 的 `runtime.startup` 行），**不写入 `company.json`**——冷启动一律新建 owner，无需回读旧 id。
- **所有员工会话（含 resident 经理）都是 owner 的直接子级**：`subagents.startActivation({ ..., request: { parent: ownerHandle.agent } })`。部门只是账本里的逻辑映射，不是会话挂载点。
- **冷启动策略（B3）**：进程崩溃/DSH 重启后旧 owner 实例已不存在（subagent resident 目录随旧进程消失，resume 出来的新实例 ≠ 旧实例会导致旧 child 引用 `UNAUTHORIZED`）。因此 **boot 一律 create 新 owner**（ownerSessionId 重新生成并记入审计流），resident 经理用 `ctx.agents.resume({ resumeSessionId, parentAgent: ownerHandle.agent })` 恢复为新 owner 的直接子级；账本里 running/queued 但无活会话的 attempt 标 stale 并回收/重派。
- **startActivation 必须显式传 `cwd: dataDir`**（默认 cwd = owner 的 workingDirectory，根级 owner 会落到 ctx.workspace/插件目录，污染工作区）。
- **shutdown（I6 优雅停工，严格顺序）**：①停派工（runtime 层拒绝新 assign/report，只记审计）→ ②给每个 live child followup 一条「停工」信号 → ③`Promise.race([所有 whenIdle, 10s timeout])`（保证最后 chunk 的 usage 落账）→ ④逐个 `cancel(cause, { keepInbox: true })` → ⑤`subagents.drainChildren(ownerHandle.agent, 所有 live childIds)` 作为唯一清理路径（内部既做 dispose 又清 subagent bookkeeping 并等 settled）→ ⑥`ownerHandle.dispose()` → ⑦写审计。
- **tools.guard 是同步函数**：`agent.ctx.tools.guard((exec) => reason | undefined)`，同步返回非空字符串才拒绝；`exec.agent.session.id` 即 childId，用它反查 `Map<childId, Line>`。行隔离三保险 = restrict（挡继承层）+ guard（真正硬拒）+ 执行体反查（四线共用同一套三保险）。
- `ctx.agents` 不可用 / owner 恢复失败：boot 返回 `warnings`，工具返回 `E_NO_AGENTS`，**不抛**；下次调用重试建立。

### 2.4 会话/员工规则

- 员工身份持久、会话一次性；`per_task` 员工每单新会话（幂等键 `orderId:attemptId`），`resident` 经理常驻。
- 同一员工同一时刻最多一个在岗 attempt（互斥在 dispatcher 层保证）。
- `company_report` 必须带 `attemptId`；陈旧 attempt 返回 `{ ok:false, code:"E_STALE_ATTEMPT" }` 并记审计。
- 员工忘回报兜底：`tool/result` 与 `assistant/message` 观测 → 超 `lostReportGraceMs` 由调度器标 `lost` 并唤起经理复核（三重保障见规格 §11）。

## 3. 集成点（负责人：Lead）

`lib/index.js`：
1. **不扩 inject**（保持 `["tools","webServer"]`）：cordis 中 inject 的服务若缺失会让 `apply` 等待、插件整体不加载，违反「降级不阻塞加载」。其余服务（agents/subagents/llm/systemPrompt）一律 `ctx.get(name)` **惰性解析**（现有 lib/index.js 对 agentTeams 即此写法），boot 发现缺失时按退避重试并给 warnings。
2. `apply()` 末尾：`const company = createCompanyRuntime(ctx, { dataDir, config: cfg })`；`company.tools.forEach(register)`；路由 `API_PREFIX + "/company" + path` 并入现有 web 注册；`ctx.effect(() => { company.boot(); return () => company.shutdown(); })` 或等价幂等启动，**不 await、不阻塞 mount**。
3. `GET /state` 增 `company: { enabled, status, dbg }` 摘要；`GET /company/overview` 返回组织树 + 工位看板 + 成本视图数据。
4. config 透传：`cfg.org / cfg.limits / cfg.toolPolicies / cfg.company`。
