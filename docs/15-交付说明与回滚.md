### 3.2 从旧版切换（推荐用脚本）

> **0.3.0 起推荐一键迁移（尤其 npm 安装场景）**：
> ```bash
> node scripts/migrate-old-plugin.mjs            # dry-run 看计划
> node scripts/migrate-old-plugin.mjs --apply    # 切换 profile + 写数据迁移标记
> ```
> 它会改 profile 三处、删旧包目录，并写 `~/.dsh/storages/member-manager/pending-migration.json`；新插件**首次启动自动**执行名册→公司化迁移（`syncRoster` + `importRosterProfiles`），完成后删除标记并在 `audit.jsonl` 记录 `company.migration_started/completed`。已在新包上的用户可只写标记：`--data-only --apply`。

```bash
# 1) 先 dry-run 看差异
node scripts/switch-to-dsh-member-manager.mjs

# 2) 确认后写入（会先备份 profile package.json 与 node_modules 链接状态）
node scripts/switch-to-dsh-member-manager.mjs --apply

# 3) 完全退出 DSH 后重启（不要只刷新页面）
```

手工切换等价步骤（任选其一，脚本即封装此流程）：

1. 备份 `~/.dsh/profiles/desktop/package.json` 与 `node_modules/dsh-plugin-member-manager` 链接信息；
2. `dependencies` 中把 `dsh-plugin-member-manager` 改为 `dsh-member-manager`，值指向新目录；
3. `dsh.profile.bundles` 中换成 `dsh-member-manager`；
4. `node_modules` 里删旧链接、建新链接（Windows：`mklink /J`；脚本用 Node `fs.symlink`/junction）；
5. 删除 profile `cordis.yml` 里旧的 `- id: dsh-plugin-member-manager` 条目（若存在）；
6. 重启 DSH，验证：
   ```bash
   curl -s http://127.0.0.1:<port>/api/dsh-member-manager/health
   ```

> ⚠️ DSH 运行中不要替换插件目录本身；切换的是 profile 的**引用**，不移动源码。旧仓库
> `C:\Users\Ren\Documents\deepseek-harness\default-workspace\dsh-plugin-member-manager` 保持不动，作为回滚基线。

## 4. 回滚

```bash
node scripts/rollback-to-dsh-plugin-member-manager.mjs          # dry-run
node scripts/rollback-to-dsh-plugin-member-manager.mjs --apply  # 写回旧版引用
# 完全退出 DSH 后重启
```

手工回滚 = 第 3.2 节的逆操作（依赖名/`bundles`/`node_modules` 链接/cordis 条目全部换回 `dsh-plugin-member-manager`）。
回滚后名册数据仍可用（目录与格式未变）；公司化数据（`company.json`、`ledger/`、`audit/`）旧版不读取，但**不会删除**，可保留或手工清理。

## 5. 兼容性与降级矩阵

| 场景 | 行为 |
| --- | --- |
| 宿主无 `agents`/`subagents` 服务 | 名册 16 工具 + 面板 + 路由正常；`company_*` 返回 `E_NO_AGENTS`；boot 只 warning |
| `company.enabled=false` | `company_*` 返回 `E_DISABLED`；启动不 boot；名册功能不受影响 |
| 公司 runtime 构造/boot 抛错 | apply 继续完成；`GET /state.company.error` 可见；名册功能不受影响 |
| Agent 服务晚到（cordis 动态注册） | boot 用 `ctx.effect` 挂载、`ctx.get` 惰性解析；不阻塞 apply |
| 上一次进程崩溃（B3） | 冷启动**重建** owner（新 `ownerSessionId`），resident 经理 resume 为新 owner 直接子级；账本里遗留 running/queued attempt 标 stale 后回收/重派 |
| 员工会话 cwd | 所有 `startActivation` 显式 `cwd: dataDir`，不污染插件目录/工作区 |
| 关闭插件 | `ctx.effect` disposer → 停派工 → 等 idle（超时）→ cancel(keepInbox) → `drainChildren(owner)` → dispose owner → 审计落盘 |
| 工具越权 | 会话级同步 `tools.guard` 只限制 `company_*` 公司工具（按线白名单）+ 执行体反查，返回 `E_TOOL_LINE`；宿主标准工具（读写/bash）保留给员工以完成实际工作（v5.24） |

## 6. 数据与权限

- 公司化只写 `~/.dsh/storages/member-manager/company/`：`company/company.json`（权威快照）、`company/audit.jsonl`（append-only 审计流）、`company/ledger/*.jsonl`（checkpoint 日志）、`company/workspace/`（员工会话 cwd）。
- 单实例锁：`company.json` 之外的 `.lock` 文件，启动时抢占，超时可回收（见 docs/11 §1.2）。
- 审计 append-only；账本按工单分文件，损坏文件降级为 warning 不抛。
- 公司化运行时自身不执行任意外部命令；员工的 `company_*` 工具面按线白名单限制，宿主标准工具保留。

14. **名册同步语义**：`syncRoster` 只增不降级——名册里新增的分组/成员会建部门/员工，已存在成员只更新显示名与部门，**不会**改 role/level/code，也不会因名册删除而删员工或降级负责人；名册移除的分组/成员需手工停用（`fireEmployee`）或删除（`deleteDepartment`，仅空部门）。
15. **M/P 通道并存（v5）**：员工 `channels` 至少 1 个；`manager` 必含 M、`window` 禁 M、`staff` 可 M+P；旧字段 `channel`/`level` 始终由 `channels` 推导（含 M 则主通道 M）。「管理层」节点只是按 M 通道聚合的**只读视图**，不改变员工部门归属、代码层级或权限；部门卡 M/P 分栏与 KPI 按通道各计一次，故含双通道的员工会计入两个通道的计数（员工总数仍按人去重）。
16. **技能/模型选择器（v5.5）**：人事详情改为从 `GET /skills` 与 `GET /models` 目录选择；目录外的技能名、模型/provider id 不能手填（模型弹层含「使用默认」可清空覆盖）。技能目录为空或宿主无 `ctx.get("skills")` 时弹层显示空列表，保存时按当前草稿提交。

17. **职责条目与名册（v5.7 / v5.9）**：岗位职责按条目编辑、最多 8 条（保存自动 trim/过滤空行/截断）；v5.9 起名册分组与相关 UI 已移除——`registry.json` 的 3 个分组已删除、13 名成员未分组（备份 `~/.dsh/backups/registry-before-group-removal-20261021T142037.json`），host 侧 `syncRoster` action 仍存在但面板不再暴露；v5.10 起「导入名册资料」按钮也移除（host `importRosterProfiles` action 保留）。
19. **总架构编辑（v5.11 / v5.12 / v5.12.1）**：管理层名称限 1–40 字符（仅影响架构图显示，默认「管理层」）；编号模板必须含 `{seq}`/`{seq:N}`，可用占位符限 `seq`/`dept`/`channel`/`level`，起始号为正整数，弹层内含占位符用法说明；等级通道可改通道名称/说明与各级名称，**v5.12 起可增删等级**（代号须为通道字母+正整数、每通道 ≥1 级），**删除靠前等级后后续等级自动顺位**，员工等级按 `levelRemap` 同步改写；删除仍被员工引用且无法映射的等级报 `E_LEVEL_IN_USE`；面板编辑器提交即持久化到 `company.json`，审计分别记 `company.management_renamed` / `numbering_set` / `company.levels_set`。

18. **名册档案迁移（v5.8）**：`importRosterProfiles` 只把名册 active 成员的档案**补进空字段**（显示名/岗位/职责/技能/模型覆盖），绝不覆盖公司化侧已有值；需要以名册为准覆盖时先手工清空对应公司化字段再导入。迁移完成后名册分组即可安全删除（`deleteGroup`，成员变未分组），公司化组织与工单不受影响；名册成员记录本身不建议删除（导入来源与历史追溯）。

20. **旧包升级迁移（v5.25）**：`migrate-old-plugin.mjs` 只改 profile 三处 + 写 `<dataDir>/pending-migration.json`，不直接改 `registry.json`；真正的名册→公司化转换由新插件 boot 时一次执行（`syncRoster` + `importRosterProfiles`），只迁 active 成员、只补空字段，幂等且失败最多重试 3 次（之后标记改名 `.failed` 并停止重试，可手工删除后重启再试）。迁移不会删除名册成员记录；迁移完成后名册分组仍可保留或另行删除。

21. **旧包名转发包（v5.26）**：npm 不支持包名重定向，旧包名 `dsh-plugin-member-manager` 的可用性由 `compat/dsh-plugin-member-manager/`（0.3.1，依赖 `dsh-member-manager@^0.3.0`）承接；发布顺序必须先发主包再发转发包，且发布前用临时 profile 实测加载；两个包不得同时启用。主包已移除 `repository` 字段，发布不依赖 GitHub 仓库。
