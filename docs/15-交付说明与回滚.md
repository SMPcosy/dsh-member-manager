- profile 的 `cordis.yml` 中出现 `- id: dsh-member-manager` / `name: dsh-member-manager` 条目（由 bundle patch 插入）。

### 3.2 从旧版切换（推荐用脚本）

```bash
# 1) 先 dry-run 看差异
node scripts/switch-to-dsh-member-manager.mjs

# 2) 确认后写入（会先备份 profile package.json 与 node_modules 链接状态）
node scripts/switch-to-dsh-member-manager.mjs --apply

# 3) 完全退出 DSH 后重启（不要只刷新页面）
```

手工切换等价步骤（任选其一，脚本即封装此流程）：

1. 备份 `~/.dsh/profiles/desktop/package.json` 与 `node_modules/dsh-plugin-member-manager` 链接信息；
2. `dependencies` 中把 `dsh-plugin-member-manager` 改为 `dsh-member-manager`，值指向新目录；
3. `dsh.profile.bundles` 中换成 `dsh-member-manager`；
4. `node_modules` 里删旧链接、建新链接（Windows：`mklink /J`；脚本用 Node `fs.symlink`/junction）；
5. 删除 profile `cordis.yml` 里旧的 `- id: dsh-plugin-member-manager` 条目（若存在）；
6. 重启 DSH，验证：
   ```bash
   curl -s http://127.0.0.1:<port>/api/dsh-member-manager/health
   ```

> ⚠️ DSH 运行中不要替换插件目录本身；切换的是 profile 的**引用**，不移动源码。旧仓库
> `C:\Users\Ren\Documents\deepseek-harness\default-workspace\dsh-plugin-member-manager` 保持不动，作为回滚基线。

## 4. 回滚

```bash
node scripts/rollback-to-dsh-plugin-member-manager.mjs          # dry-run
node scripts/rollback-to-dsh-plugin-member-manager.mjs --apply  # 写回旧版引用
# 完全退出 DSH 后重启
```

手工回滚 = 第 3.2 节的逆操作（依赖名/`bundles`/`node_modules` 链接/cordis 条目全部换回 `dsh-plugin-member-manager`）。
回滚后名册数据仍可用（目录与格式未变）；公司化数据（`company.json`、`ledger/`、`audit/`）旧版不读取，但**不会删除**，可保留或手工清理。

## 5. 兼容性与降级矩阵

| 场景 | 行为 |
| --- | --- |
| 宿主无 `agents`/`subagents` 服务 | 名册 16 工具 + 面板 + 路由正常；`company_*` 返回 `E_NO_AGENTS`；boot 只 warning |
| `company.enabled=false` | `company_*` 返回 `E_DISABLED`；启动不 boot；名册功能不受影响 |
| 公司 runtime 构造/boot 抛错 | apply 继续完成；`GET /state.company.error` 可见；名册功能不受影响 |
| Agent 服务晚到（cordis 动态注册） | boot 用 `ctx.effect` 挂载、`ctx.get` 惰性解析；不阻塞 apply |
| 上一次进程崩溃（B3） | 冷启动**重建** owner（新 `ownerSessionId`），resident 经理 resume 为新 owner 直接子级；账本里遗留 running/queued attempt 标 stale 后回收/重派 |
| 员工会话 cwd | 所有 `startActivation` 显式 `cwd: dataDir`，不污染插件目录/工作区 |
| 关闭插件 | `ctx.effect` disposer → 停派工 → 等 idle（超时）→ cancel(keepInbox) → `drainChildren(owner)` → dispose owner → 审计落盘 |
| 工具越权 | `tools.restrict` 白名单 + 同步 `tools.guard` + 执行体反查，返回 `E_TOOL_LINE` |

## 6. 数据与权限

- 公司化只写 `~/.dsh/storages/member-manager/company/`：`company/company.json`（权威快照）、`company/audit.jsonl`（append-only 审计流）、`company/ledger/*.jsonl`（checkpoint 日志）、`company/workspace/`（员工会话 cwd）。
- 单实例锁：`company.json` 之外的 `.lock` 文件，启动时抢占，超时可回收（见 docs/11 §1.2）。
- 审计 append-only；账本按工单分文件，损坏文件降级为 warning 不抛。
- 公司化运行时自身不执行任意外部命令；员工工具面按线白名单限制。

## 8. 已知限制

1. **工作副本**：本版交付位于 `C:\Users\Ren\Documents\deepseek-harness\插件工作区\dsh-member-manager`，旧仓库保留为回滚基线；`package.json.repository` 指向 GitHub 新仓库（若远端尚未创建，发布前需先建仓或改回）。
2. 公司化面板 UI：「总架构」为组织架构图 + 只读 KPI/成本（5s 轮询，读 `GET /company/overview`）；部门弹层「成员详情列表」**可写**（招聘 / 晋升 / 停用 / 调岗，走 `POST /company/op`，与工具共用锁与审计）；新建部门可创建公司化部门；v4.1 起工具栏「从名册同步」可把成员名册同步为公司化组织，部门弹层底部可「删除部门」（仅空部门）。仍未做：面板内编辑编号模板/等级目录（用 `company_admin.setNumbering` 或配置）、工单/派工操作（用 `company_*` 工具）。
3. `ORDER_STATES` 按冻结测试集实现（无 `blocked`/`review` 状态），验收/返工用 attempt 状态 + acceptance 结果表达（裁决见 docs/11 §1.4）。
4. 旧文档 docs/00–10 中的旧包名/旧安装路径是历史记录（docs/03/06/07 明确保留），以 `README.md` 与本文件为准。
5. **`company.limits` 仅做结构校验与调度 tick**（`staleAttemptMs`）；`maxConcurrentPerProvider` / `maxTemps` / `budgetTokensPerDay` / `lostReportGraceMs` 的强制闸门是后续里程碑，当前不会拒绝派工或超预算工单。
6. **持久化强度**：`company.json` 用 tmp+rename 原子替换但未 `fsync`；`audit.jsonl` 单次 append 在 Windows 下非原子（单进程内由文件锁保护）。极端断电可能丢最后一条审计。
7. **冷启动残留会话**：冷启动一律新建 owner，旧进程的 resident/临时工会话由 subagent 持久化层自然回收，本版不显式 `drainDescendants`（旧 owner 实例已不可达，无稳定句柄）；账本侧只回收 running/queued attempt。
8. **成本归因粒度**：`assistant/message` 是会话事件，通过子 Agent 的 `ctx.on("session/event", …)` 累加（找到子 Agent 之前轮询最长 5s）；若宿主侧拿不到子 Agent（例如非 local provider），只累计 owner 自身用量，`/company/costs` 会偏低。本版已在真实宿主对账（45021 tokens / 6 请求与子会话逐条相等）。成本为**进程内**统计，重启清零。
9. `company_admin` 本版支持 `createDepartment` / `createEmployee` / `updateDepartment` / `promoteEmployee` / `setRoutingRules` / `setNumbering`；暂停 / 恢复 / 改编制（capacity）/ 预算 / 解雇仍未开放（解雇用名册层 `member_remove`，不联动公司账本）。
10. **provider 默认名**：`company.provider` 默认 `spawn`（宿主内置 provider 名）。若目标宿主未启用 spawn provider，需在配置中显式改成已注册名（如 `fork`），否则派工返回 `NO_PROVIDER`；本版不做自动探测回退。
11. **等级目录与编号模板的自定义入口**：只能通过组织配置 `company.levels` / `company.numbering` 或运行时 `company_admin.setNumbering` 修改；面板暂不提供编辑器。等级目录改动后，已有员工等级保持不变（不自动重排）；非法目录整体回退默认并记 warning。
12. **跨通道/晋升约束**：同通道晋升只能 ±1 级；跨通道必须显式指定 `level` 且 `role` 跟随（window 不可转 M，转 M 前必须有部门）。历史数据补号补级只在 boot 时执行一次，外部手改 `company.json` 后需重启生效（或以工具操作）。
13. **业务实体 id 生成**：`POST /company/op` 缺省 id 为 `dept-<base36>-<4位随机>` / `emp-<base36>-<4位随机>`（与既有 nanoid 风格一致，非加密随机）；重复 id 会被 shared 层拒绝，不会写坏数据。ownerSessionId 已使用 `crypto.randomUUID`。后续统一 id 策略时再收敛（独立审阅 R2，裁决不修）。
14. **名册同步语义**：`syncRoster` 只增不降级——名册里新增的分组/成员会建部门/员工，已存在成员只更新显示名与部门，**不会**改 role/level/code，也不会因名册删除而删员工或降级负责人；名册移除的分组/成员需手工停用（`fireEmployee`）或删除（`deleteDepartment`，仅空部门）。
