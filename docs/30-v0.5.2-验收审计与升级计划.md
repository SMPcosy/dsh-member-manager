## 2. 修了什么

### 2.1 异常清不掉：一个必然抛错 + 三个口径错误

| 层 | 根因 | 修法 |
|----|------|------|
| 后端（致命） | `clearExceptionHistory` 分支里调用了该文件作用域不存在的 `withLedger` / `persist` / `append`，每次点击必抛 `ReferenceError`，被外层 catch 吞成 `{ok:false, code:"E_INTERNAL"}`，账本一条没删 | 改用本文件真实可用的 `store.withLock` + `store.load` + `store.saveLedger` + `store.appendAudit`（`src/host/company-runtime.mjs:1380`） |
| 后端（口径） | 老账本里存在 `state=failed` 但无 `endedAt` 的单：前端既不算「活异常」也不算「已关闭异常」，清理按钮永远 disabled → 僵尸单 | 清理按终态判定（`cancelled` / `lost` / `failed`），不再要求 `endedAt`（同上 :1397） |
| 前端（交互） | 用 `window.confirm` 做二次确认，宿主 Web 环境常被拦或直接返回 false，点了像没反应 | 改两段式按钮：首点「再点一次确认」上膛、3 秒自动复位、次点才发请求（`lib/client.js:6564`、`:7037`） |
| 前端（观感） | KPI「异常」用 `buckets.abnormal.length`（含 11 条历史 cancelled），泳道 count 用活异常数（0），看起来「异常 11 一直清不掉」 | KPI 改 `liveAbnormal.length`，历史数挂在范围开关上，chip 加 `title` 说明（`lib/client.js:6972`、`:6982`） |

清理后的索引同步：删单后调用 `dispatcher.rebuildIndexFromLedger()`，避免调度器拿着孤儿 attempt 去唤醒员工（`company-runtime.mjs:1416`）。

审计留痕：每次清理写 `{type:"exception_history_cleared", count, orderIds, sessionId}`。

### 2.2 已完成倒序 + 会话指向

- 服务端：`lib/index.js:987` 起，排序键 = 关闭单取 `endedAt`、未关闭取 `createdAt`，降序。**只按 `createdAt` 不够**：先建后交的长任务会挤到刚交的活前面，而这个顺序同时决定 `pipeline.done`。
- 客户端：删掉 `if (key === "done") list.reverse()`（旧版对已排好的数组又反一次，导致最旧在前）。
- 卡片：`attemptNo` 后加会话徽标（`会话 <标题前16字>`，`title` 带完整标题 + sessionId），并显示结束时间（近 24h 用 `3h12m`，更早用 `MM-DD HH:mm`）。

### 2.3 已完成跟随会话归档

会话归属从「只有屏幕上的 taskId」变成**账本字段**：

| 入口 | 写入位置 | 行为 |
|------|----------|------|
| `company_order` 工具 | `company-runtime.mjs:268 sessionStamp(exec)` → `:299` | 从 `exec.agent.session` 取 root（`header.parentSession \|\| id`）+ 标题快照 |
| `company_plan` 工具 | `:290 withSessionStamp` → `:308` | 整批任务图共享同一归属 |
| 看板「新建订单」 | `lib/client.js:7263` 附 `sessionArgs()` | 面板派的活也归当前会话 |
| 看板「手动派工」 | `lib/client.js:7185` → `dispatcher.stampSession`（`company-dispatcher.mjs:279`） | 只补空缺，已有归属不覆盖，写 `order_session_stamped` 审计 |

前端归档规则（`lib/client.js:6961`）：

- 默认 `archivedScope = true`：done 泳道与异常记录区只显示 `sessionId === 当前会话` 的单；**无归属的老单视为本机遗留，留在当前会话里**（否则它们永远藏在归档中，既看不见也清不掉）。
- 头部范围开关 `data-mm-scope`：`只看本会话 · +N` ⇄ `全部会话`，`N` = 被归档掉的数量，点一下就能回看。
- 清理按钮按范围传 `{sessionId}`，只清本会话的异常历史，不误删别的对话。

### 3.4 已知遗留（本次**没有**做，不算缺陷但要知道）

1. **清理是硬删**：账本里真删，只有 `audit.jsonl` 留 `orderIds` 可查，无界面级的撤销。
2. **`view.orders` 仍是 `ledger.orders.slice(-50)`**：按账本插入序取尾部 50 单；长期运行、单量过百后，早期的未关闭单可能被挤出视图。这是既有行为，本次未动。
3. **归属记「首建会话」**：订单被别的会话接管后不会改归属（有意为之，避免单据在会话间漂移）。
4. **老账本 29 单没有 `sessionId`**（cancelled 11 / done 18）：它们都算「本机遗留」，任一对话里点一次清理都会把 11 条取消单一起清掉——这正是用户要的效果，但**不可逆**。

## 4. 下一步升级改进计划

路线衔接既有 [ROADMAP.md](./ROADMAP.md)（v0.6.0 硬闸门 + 成本持久化 → v0.7.0 观测 → v1.0.0 量化成熟）。本次看板改造产生的新差距插在 v0.5.3 / v0.6.x。

### 4.1 v0.5.3 · 归档收尾（建议先做，工作量 ≈1 天）

| 项 | 内容 | 验收口径 |
|----|------|----------|
| 软删除 | 清理改为写 `archivedAt` + `archivedBy`，视图过滤，保留 30 天后由调度器物理回收 | 清理后账本仍在、视图消失；`restore` op 能捞回；测试断言 archivedAt 落库 |
| 视图窗口 | `view.orders` 由 `slice(-50)` 改为「未关闭全量 + 已关闭最近 50」，按 `state` 分流 | 造 60 单（55 closed + 5 open）时 5 张活单必在；断言不依赖插入序 |
| 会话分组 | 「全部会话」下 done 泳道按 `sessionId` 分组小标题（本会话置顶），异常记录区同 | 三会话混排时能一眼看出归属；client 测试断言分组标题数 |
| 归档检索 | 头部加会话下拉（来自 orders 去重），选中即过滤，等价于手工切 scope | 下拉项与账本会话集合一致 |

### 4.2 v0.6.0 · 硬闸门 + 成本持久化（ROADMAP 既定，优先级最高）

| 项 | 内容 | 验收口径 |
|----|------|----------|
| 并发闸门 | `maxConcurrentPerProvider` 派工前查活 attempt 数，满则 `E_CAPACITY` 退避 | 超并发派工被拒且可复现；退避不误杀空位单 |

### 4.3 v0.6.x · 观测与可维护性

1. **subagent 树**：一屏看父→子代理与产出（抄 command-centre 的长处，只读叠加）。
2. **`lib/client.js` 拆分**：7862 行单文件、手写 bundle、无类型。拆成 `client/board.js`、`client/chart.js`、`client/forms.js`、`client/i18n.js`，构建脚本内联；同时加 `tsc --checkJs`（作为 devDependency，零运行时依赖不变）。
3. **会话归档的导出**：按会话导出 done/异常明细（Markdown / CSV），支持「把这次会话干了什么」直接归档进共享库。

### 4.4 v1.0.0 · 量化成熟（ROADMAP 不变）

派工基准（首层并行率 / 下游放行延迟 / 吞吐 / 故障自愈覆盖率 / 成本归因准确度）可复现、可横向对比；面板批量操作（批量验收 / 取消 / 派工）；正式发布。

### 4.5 取舍与风险

| 风险 | 影响 | 应对 |
|------|------|------|
| 软删除让账本只增不减 | `company.json` 体积膨胀（现 271KB / 29 单） | 30 天回收 + 归档单压缩成摘要行（保留 id/state/endedAt/sessionId） |
| 预算硬拦误伤长任务 | 合法任务被拒 | 只软拦截 + 告警 + 人工放行（沿用 ROADMAP 决策） |
| 自动重试放大成本 | 坏任务烧 token | 重试上限 + 指数退避 + 同因连续失败即停 |
| client 拆分回归风险 | 面板白屏 | 拆分前后跑同一套 56 条 client 测试作等价性判据 |

## 5. 决策记录

| 日期 | 决策 | 理由 |
|------|------|------|
| 2026-11-03 | 异常清理按终态判定，不再要求 `endedAt` | 老账本里 failed 无 endedAt 的单按旧口径永不入历史区，是真僵尸单 |
| 2026-11-03 | 清理按 `sessionId` 划范围，无归属老单跟随当前会话 | 否则老单既不在本会话可见、也无法被任何会话清掉 |
| 2026-11-03 | 归属只记首建会话，不随接管改写 | 单据在会话间漂移会让「这次会话干了什么」失去意义 |
| 2026-11-03 | 确认交互从 `window.confirm` 改按钮两段式 | 宿主 Web 环境会拦 confirm，用户感知就是「点了没反应」 |
| 2026-11-03 | 排序键用 `endedAt || createdAt`，不用纯 createdAt | 排序同时决定 `pipeline.done`，长任务不能压住刚交的活 |
| 2026-11-03 | 本轮发 v0.5.2，不直接跳 0.5.3 | 改动已闭环且测试全绿，先发修好的版本止损；0.5.3 的软删除/分组是增量，不该拖着修好的 bug 不发 |
