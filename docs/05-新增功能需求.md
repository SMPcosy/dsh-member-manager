## 功能 1 · 让成员可以修改模型

**用户选择**：**尝试真正切换**（明知内核无此能力）。

### 已确认的约束（源码证据）

| 事实 | 证据 |
|------|------|
| 成员的 `model` 是**派生只读**，不落盘 | `_dsh_ref\dsh-experimental-agent-team\lib\types\roster.js:112`（Lead 行）、`:117`（`const model = live?.options.model ?? root.options.model`）、`:130`（teammate 行）、`:413` |
| `spawnTeammate` 的 request **没有 model 字段** | `roster.js:222-262`（逐字段可查） |
| 成员身份字段被投影层强制不可变 | `lib\types\projection.js:199-204` |
| 内核类方法全集无任何 model setter | `lib\types\index.js:86-212` |

⇒ **官方没有提供修改成员模型的接口**。用户已知悉风险并要求尝试。

### 实现状态：✅ 已完成 —— **真生效，不是覆盖层降级**（2026-10-15，全仓 118/118 测试通过）

关键发现：内核确实**没有** setter，但官方为插件留了一个正式的**水位（waterfall）接缝**，而且官方自己就用它做模型选择。

**证据链**：
1. `dsh-agent-loop\lib\index.js:1163-1183` —— `prepareRequest()` 每轮都读 `this.options.provider/model` 组成 `seedConfig`，然后
   `const proposedConfig = await this.dispatch.waterfall("agent/request", { turn, step, signal }, () => Promise.resolve(seedConfig));`
   返回什么，就用什么发请求。
2. `dsh-agent\lib\types\model-selection.js:61` —— 官方实现就是：
   ```js
   const disposeRequest = agentCtx.on('agent/request', async (_payload, next) => {
     const resolved = await next();
     const selected = selection.assembled;
     if (selected === undefined) return resolved;
     return { ...resolved, provider: selected.provider, model: selected.model, ... };
   });
   ```
3. 钩子挂在**该 agent 的作用域 ctx** 上（`agent.ctx`），所以天然「按成员」生效。
4. 遍历与安装的官方范式：`dsh-experimental-tool-agent-team\lib\index.js:543-544`
   ```js
   for (const agent of ctx.agents.list()) maybeInstall(agent);
   ctx.on("agent/created", ({ agent }) => { ... maybeInstall(agent) ... });
   ```

**本插件的实现**：
- 每个 agent 上装两个监听：`agent/request`（改写实际请求配置）与 `system-prompt/assemble`（同步系统提示里的 provider/model 变量，官方同样这么做）
- 覆盖值来自名册：`members[].model` / `members[].provider`；成员名通过 `agentTeams.tryMembership(agent).name` 取得
- 名册读取带短 TTL 缓存（`agent/request` 每轮都触发，不能读盘）；`TeamService` 新增 `onWrite` 回调，**任何成功写入都立刻失效缓存**，所以设完模型下一次请求就生效，不用等 TTL
- 停用（retired）成员的覆盖自动失效
- 新工具 `member_set_model`（`model` 传空串即清除覆盖）；面板编辑表单加了模型与 provider 输入框，成员行显示模型徽标

**追加：模型目录（避免填错 model id）**

真机测试时我给成员填了一个不存在的 `deepseek-pro`，这**不会报错、但会让该成员后续请求失败** —— 静默踩坑。于是补上了官方目录接口：

- `ctx.llm.listProviders()` → `LlmProviderInfo[]`（注册顺序）
- `ctx.llm.listModels(provider)` → `LlmModelInfo[]`，形状见 `dsh-llm\lib\types\index.js:487-493`：`{ id, name?, contextWindow?, maxTokens?, inputModalities? }`
- README 原文：「GUI 的模型选择与提交要求模型出现在目录中」，即目录驱动入口本就该这么做

据此新增 `model_list` 工具与 `GET /models` 路由；面板的模型输入框上方多了一个**下拉选择**（选项形如 `deepseek-account · deepseek-flash`），选中时**同时写入 provider 与 model**。目录外的 id 仍可手填（README：目录成员资格不约束核心路由）。

同时修掉一个设计缺陷：清除模型时会留下**孤立 provider**（没有 model 的 provider 无意义，只会在界面造成困惑）—— 现在清空 model 会一并清掉 provider。

**真机验证记录（2026-10-15）**：
- `boot.log`：`tools-done:ok=11 failed=0`、`routes-registered:4`、`apply-completed:tools=11 routes=4`
- **`model-override-installed:session-27c572e4-b329-4267-99b2-1cba2314891c`** —— 模型覆盖监听确实装到了真实 agent 上（`agents-preinstalled:0`，说明是加载后由 `agent/created` 补装的，正是本次修好的那条路径）
- `skill_list` 真机调用成功（此前报 `value is not lossless JSON`，修复后正常）
- `member_set_model` 真机调用成功：设置 → 读回 → 清除，均返回预期结果

**仍未做的验证**：没有让一个真实成员**用不同模型跑一轮**，因此「覆盖后的模型确实被用于生成」这一步只有单元测试（5 条）+ 官方接缝证据支撑，没有端到端观察。要补这一步需要一个可用模型 + 跑一个 teammate 并核对其会话里持久化的 `config.model`。

**顺带修掉的两个缺陷**：
1. `agent/created` / `agent/status` 的官方载荷是 `{ agent }`，而旧代码把载荷直接当 agent 用 —— 事件路径**从未**成功刷新过缓存。现在按官方形状解构，并容错直接传 agent 的写法。
2. `skill_list` 给 `whenToUse`/`path` 赋 `undefined`，而 DSH 校验工具输出能否**无损 JSON 往返** → 真机调用报 `value is not lossless JSON`。改为「只在有值时挂键」，并新增一条对**全部 11 个工具**做往返校验的测试，防止整类问题复发。

**风险与未证实项**：
- 本机的**实际效果未经真机验证**（需要再重启一次 DSH 才能在界面上操作）。逻辑层已由 5 条测试覆盖：真写进请求配置、不丢 seed 其它字段、系统提示变量同步、写完立即生效、停用后失效。
- 与官方 `model-selection` 并存时是**水位叠加**：谁在链上更靠后谁说了算，未被 A/B 隔离验证。

### 原降级方案（未采用，仅存档）

按覆盖层语义在名册里记录「该成员应使用的模型」并展示，但**明确标注它不改变实际运行模型**。因为找到了正式接缝，未走此路。

### 问题 2 · 改模型不生效 —— 已修（真根因）

**现象**：面板里改模型、保存，没有任何效果。

**模型从未被写进名册**。我加了 `service.setModel` 和 `member_set_model` 工具，却漏了面板要用的那一环。

**修复**：补上 `setModel: (a) => service.setModel(a.target, { model: a.model, provider: a.provider })`。

**防复发**：新增一条**客户端/宿主契约测试** —— 从 `lib/client.js` 里把 `post("...")` 与 `run("...")` 的操作名全部抓出来，
逐个打真实 `/op` 路由，任何一条没接线都会断言失败。这类「加了功能忘了接线」的问题以后跑测试就会被拦下。

**另外**：面板的模型下拉数据源 `/models` 实测正常，本机真实模型 id 是 `deepseek-v4-pro`
（我此前测试时误用了不存在的 `deepseek-pro` —— 这正是我加下拉选择的原因）。

`setModel` 清空模型时会留下**孤立 provider**（没有 model 的 provider 无意义）。现在清空 model 会一并清掉 provider。

## 第四轮：模型覆盖的端到端验证（拿到铁证）

### 为什么之前证明不了

DSH 的**会话投影不记录每轮请求用的模型**。查遍 `storages\session_projcache\sessions\*.json`、
`~\.dsh\logs\`、`~\.dsh\sessions\`，只有 GUI 自己的 `modelSelection.lastUsed`（那是官方模型选择器的状态，
与本插件的覆盖无关），没有任何 `requestHeader().config` 的落盘。所以「覆写有没有真的发生」从外部看不见。

### 解决：给插件加可观测性

这本来就是它缺的东西 —— 一个「隐形」的功能，出问题时无从判断。新增：

| 出口 | 内容 |
|---|---|
| `GET /overrides` | `installedCount` / `installed[]` / `applied` / `misses` / `lastApplied` |
| `member_diagnose` | 同样的统计（`modelOverride` 字段），便于用户自查 |
| `boot.log` | 每次覆写写一行 `model-override-applied:<target>=<model>` |

`applied` **只在覆写真正发生在 `agent/request` 水位上时才增长**，无法被伪造或误报。
