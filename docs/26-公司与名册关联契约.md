# 26 · 公司与名册关联契约（v0.3.2）

> 范围：`dsh-member-manager` 0.3.2 引入的「公司员工 ↔ 名册（registry.json 覆盖层）」双向关联。
> 目标读者：后续维护者、审阅者、需要判断「员工为什么显示未登记」的使用者。

## 1. 问题

v5.10 之后面板上的名册 UI（名册成员表、从名册同步、导入名册资料）按公司化路线移除，名册退化为
「DSH 核心成员的展示覆盖层」。但数据上仍存在两套：

| 数据 | 位置 | 权威范围 |
| --- | --- | --- |
| 公司组织 | `<dataDir>/company/company.json` | 部门、员工、岗位、通道/等级、工单、账本 |
| 名册 | `<dataDir>/registry.json` | DSH 核心成员目标的显示名/岗位/技能/模型覆盖 |

宿主里只有「名册 → 公司」方向的 `importRosterProfiles`（v5.8，只补空字段），没有反方向入口。
于是 `company_hire` / 部门和部门预设批量生成的员工（id 形如 `emp-mvhzc6kr-13qh`）只在
`company.json` 里存在，名册中没有条目 —— 员工中心既看不到「名册：已登记/未登记」，也没有
「把这些员工登记进名册」的入口。v0.3.2 补的就是这个方向。

## 2. 关联语义

### 2.1 target 解析（隐式优先）

`rosterTargetOf(employee)`：

1. 员工显式字段 `rosterTarget` 非空 → 用它；
2. 否则用员工 `id` 本身。

员工 id 天然匹配名册的 `TARGET_RE = /^[a-z0-9]+(?:-[a-z0-9]+)*$/`（`emp-*` 也一样），所以
**绝大多数员工不需要任何新字段**：`plugin-arch` 等 12 名历史员工的关联就是「id 同名」。
只有「员工 id 与希望的名册名不同」时才写 `rosterTarget`。

- 字段位置：`company.json` 的 `company.employees[i].rosterTarget`（string，可选）。
- 写入：`createEmployee({rosterTarget})` / `updateEmployee(id,{rosterTarget})` 显式设置；
  空串会删除该键。
- 校验：必须是合法成员名；非法时 `updateEmployee` 抛 `OrgError`（「名册成员名不合法：…」）。
- 迁移：老数据无该字段 → 纯隐式，零迁移。

### 2.2 关联状态

`describeRosterLink(employee, index)` 返回：

```js
{
  target: "emp-mvhzc6kr-13qh", // 生效 target
  explicit: false,             // 是否显式 rosterTarget
  status: "linked",            // linked | retired | unlinked
  available: true,             // 名册是否可读；false 时不得推断「未登记」
  member: { displayName, title, model, provider, status } | null
}
```

- `linked`：名册有该 target 且 `status === "active"`；
- `retired`：名册有该 target 但成员已停用；
- `unlinked`：名册没有该 target；
- `available:false`：读不到 `registry.json`（例如文件缺失/损坏且隔离失败），此时**不能**把员工
  显示成未登记，只能显示「名册不可用」。

### 2.3 写入原则（沿用 docs/15 §17–20）

- 名册没有该 target → 新建成员（`displayName`/`title`/`duties`/`skills`/`model`/`provider`/`note`
  来自公司档案）；
- 名册已有该 target → **只补空字段、绝不覆盖**人工维护的值；只有显式 `refresh:true` 才覆盖档案字段；
- 不删除名册成员、不改 DSH 核心 team 层；
- 名册写入统一走 `RegistryStore.save`（写 tmp + fsync + rename，旧文件保留为 `.bak`）。

## 3. 宿主 API

### 3.1 `view()` 扩展（`src/host/company-runtime.mjs`）

- `view().roster`：`{available,total,linked,retired,unlinked}`（名册不可读 → `available:false` 且计数为 0）；
- `view().org.employees[i].roster`：上述 `describeRosterLink` 结果；名册不可读 → `null`；
- 其余字段不变。

### 3.2 `company_admin` 新增 3 个 action（14 → 17）

| action | args | 语义 |
| --- | --- | --- |
| `linkEmployeeRoster` | `employeeId`（必填）、`target`（可选，仅单员工）、`refresh`、`dryRun` | 把员工档案登记进名册 |
| `syncEmployeesRoster` | `departmentId`（可选，缺省全部）、`refresh`、`onlyUnlinked`（默认 true）、`dryRun` | 批量登记（默认只处理未关联员工） |
| `unlinkEmployeeRoster` | `employeeId`（必填） | 解除**显式**关联；隐式关联返回 `cleared:false` |

`POST /company/op` 有同名 case，`source` 分别记为 `tool` / `panel`。写公司走
`store.saveCompany`，写名册走 `TeamService.linkProfiles`，审计：

- `roster.employees_linked`：`{count,created,updated,employeeIds,source}`
- `roster.employee_unlinked`：`{employeeId,target,source}`

错误码：`E_NO_ROSTER`（宿主未注入名册服务/读不到名册）、`E_NOT_FOUND`（无匹配员工）、
`E_INVALID_TARGET`（target 或员工关联名不合法）、`E_INVALID_INPUT`（缺 `employeeId`、
显式 target 用在批量场景）。

> 锁约束：`company_admin` 入口已在 `store.withLock` 内；`handleCompanyOp` 由
> `withCompanyRefresh` 持锁。`applyRosterLinks` / `unlinkEmployeeRoster` 自身不加锁
> （文件锁不可重入），两个入口各自在**已持锁**状态下调用。

### 3.3 名册工具的输出扩展（`lib/index.js`）

- `member_list` 每个成员多一个 `company`：
  `{employeeId,code,displayName,departmentId,departmentCode,role,state,explicit,linkStatus} | null`；
  顶层多 `company: {enabled,rosterAvailable,employees,linked,unlinked}`；
- `member_diagnose` 多 `rosterLinks: {available,companyEmployees,rosterMembers,linked,unlinkedEmployees}`，
  且 `plugin.version` 改为读取 `package.json`（原先硬编码 `0.1.1`，与包版本不符）。

## 4. 面板（员工中心）

- 页头右侧汇总：「名册：已登记 N · 未登记 M（· 已停用 K）」；名册不可读 → 「名册不可用
  （读不到 registry.json）」；
- 筛选下拉新增 `linked` / `unlinked`（「已关联名册 / 未关联名册」），与部门、"未启用成员"并列；
- 员工行：姓名后显示名册徽章（「名册·已登记 / 名册·未登记 / 名册·已停用」，`title` 提示生效 target）；
  未登记行尾给「登记到名册」按钮；显式关联行尾给「解除关联」；隐式关联不提供解除（避免误删名册条目）；
- 页头「批量登记未关联」：当前筛选是部门 → 只登记该部门；否则登记全部未关联员工；busy 防重复；
- 所有写操作走 `companyPost("linkEmployeeRoster"/"syncEmployeesRoster"/"unlinkEmployeeRoster", …)`，
  成功后重新拉 `GET /company/overview`。全部动态文本走文本节点，无 `innerHTML`。

## 5. CLI：`scripts/roster-link.mjs`

不依赖 DSH 运行时，直接读 `company.json` + `registry.json`：

```bash
# 只看状态
node scripts/roster-link.mjs --list [--department 内容]
# 登记某个部门（只补未关联员工）
node scripts/roster-link.mjs --department 内容
# 指定员工 / 全部 / 强制回填 / 预演
node scripts/roster-link.mjs --employee emp-mvhzc6kr-13qh
node scripts/roster-link.mjs --all --refresh
node scripts/roster-link.mjs --department 内容 --dry-run --json
```

- `--department` 接受部门 id / 编号（`D01`）/ 名称；`--employee` 可重复；
- 无范围参数时等价 `--list`（只读，不写盘）；
- `--refresh` 才覆盖名册已有档案字段；`--dry-run` 打印计划不写盘；
- `--data-dir` 缺省 `%DSH_HOME%/storages/member-manager`；
- 退出码：0 成功 / 2 参数、部门或员工不存在 / 1 其它失败；
- 写名册后追加公司审计 `roster.employees_linked`（source `cli`）；审计失败只在 stderr 提示，
  不影响已写入的名册结果。

## 8. 回滚与已知限制

- 数据回滚：`registry.json` 每次写入前的旧文件保留为 `registry.json.bak`；`company.json` 同理。
- 代码回滚：恢复本版本前的 `lib/`、`src/`、`test/` 即可；`rosterTarget` 是对老数据无影响的
  可选字段，不需要迁移。
- 已知限制：
  - 隐式关联（id 同名）不提供「解除」——解除只是删字段，删不掉名册里对应的成员；
  - 一个员工只对应一个 target；多个员工指向同一个名册成员会让后者「统计为已登记」但语义上
    建议改 id / 显式 target；
  - 面板批量登记不跨部门去重，按当前范围执行；
  - 名册读不到时面板与 CLI 都只报「不可用」，不会 fallback 到「全未登记」。

## 10. 自动登记（v0.3.3，新建部门后自动关联）

用户诉求：新建部门后不想再手动点「批量登记未关联」。

### 10.1 开关

- 配置项 `company.autoLinkRoster`（根层或 `company.org` 下），默认 `true`；`false` 关闭自动登记（创建照常，面板显示「未登记」，可手动补）。
- 校验：非布尔值回退默认并返回 warning（与 `autoBoot` 同规则）。

### 10.2 接线点（全部在创建落盘 + 审计之后，best-effort）

| 入口 | source |
| --- | --- |
| `company_hire` 工具 | `auto:hire` |
| `company_admin` → `createEmployee` | `auto:admin:createEmployee` |
| `company_admin` → `createDepartment`（补登该部门已挂员工；新部门通常 0 人） | `auto:admin:createDepartment` |
| `POST /company/op` → `createEmployee`（面板「新建部门」逐员工创建走这里） | `auto:panel:createEmployee` |
| `POST /company/op` → `createDepartment` | `auto:panel:createDepartment` |

### 10.3 语义

- 只处理未关联员工（`onlyUnlinked`）；沿用 §2.3「只补空字段、绝不覆盖」；不做 `refresh`。
- 写名册走 `TeamService.linkProfiles`（原子落盘 + `.bak`），审计 `roster.employees_linked`。
- 失败不阻塞：名册不可用（`E_NO_ROSTER`）或写失败时创建仍 `ok:true`，返回值带
  `roster:{ok:false,code,attempted,created,updated,message}`；成功带
  `roster:{ok:true,attempted,created,updated}`；关闭带 `roster:{ok:true,disabled:true,...}`。
- 锁：自动登记在创建动作已持有的公司锁内执行（`autoLinkRosterFor` 不再加锁，文件锁不可重入）。

### 10.4 测试与自检

- `test/company-runtime.test.mjs` +4：面板 op 路径自动登记、`company_hire` 自动登记、
  `autoLinkRoster:false` 关闭、名册不可用不阻塞创建。
- `test/company-config.test.mjs` 默认值补 `autoLinkRoster:true`；`test/roster-link.test.mjs`
  手动登记用例显式 `autoLinkRoster:false` 保持原语义。
- 全量 **611/611**；`node scripts/verify-company.mjs` **22/22**（「公司与名册关联」项含自动登记断言）。

### 10.5 已知限制

- 只覆盖「新建」路径；历史未登记员工（当前游戏部 7 人）仍需批量登记或
  `node scripts/roster-link.mjs --department 游戏开发`。
- 面板不展示单次自动登记结果（静默），以员工行徽章与页头汇总为准。
