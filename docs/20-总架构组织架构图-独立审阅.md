### 💡 建议级（2）

**R1（建议）fireEmployee 对不存在员工返回 E_INTERNAL 而非 E_NOT_FOUND，与 moveEmployee 不一致**
- 位置：`src/host/company-runtime.mjs:530` 直接调用 `fireEmployee(runtime.company, employeeId)`，company-org.fireEmployee（L531-537）对不存在员工抛 `new OrgError(...)`（OrgError 默认 code 未设置，见 L82-88），catch 后落到 `err.code || "E_INTERNAL"` 返回 E_INTERNAL。
- 对比：moveEmployee L546-548 显式 `if (!emp) throw {code:"E_NOT_FOUND"}`。
- 影响：停用一个不存在（或已被其他面板/Agent 删除）的员工时，面板红字显示"E_INTERNAL：员工 X 不存在"，文案误导但不影响数据一致性。属于纯文案问题。
- 最小修复：在 fireEmployee case 前置 `if (!runtime.company.employees.find(e=>e.id===employeeId)) return {ok:false,code:"E_NOT_FOUND",message:`员工 ${employeeId} 不存在`}`；或让 OrgError 默认 code="E_NOT_FOUND"。**不阻断交付**，可后续 polish。

**R2（建议）makeOpId 用 Math.random 而非 crypto.randomUUID**
- 位置：`company-runtime.mjs:428-430` `${prefix}-${Date.now().toString(36)}-${Math.random().toString(36).slice(2,6)}`，与 0.3.0 中 nanoid 使用 Math.random 是同一模式（v0.3.0 审阅时已在 docs/13 标记 I11 遗留，非新增问题）。
- 影响：部门/员工 ID 碰撞概率极低（每秒单实例下 4 位 base36 ≈ 168 万空间），且 createDepartment/createEmployee 会对重复 id 抛 OrgError 导致本次请求失败（不会写坏数据）。ownerSessionId 已改用 crypto.randomUUID（runtime L15/L491），这里只是业务实体 id。
- 最小修复（可选）：用 `${prefix}-${crypto.randomUUID().slice(0,8)}`；或保持现状与既有 nanoid 风格一致。**不阻断交付**。
