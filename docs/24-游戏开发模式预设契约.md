# docs/24 · 部门流程预设（游戏开发模式）契约

- 状态：**已实现并通过独立审阅**（v1.2；实现见 docs/25，契约语义冻结，v1.1/v1.2 为口径修订）
- 目标用户请求（原文）：「针对现有的游戏开发部门，预设一个游戏开发模式。」
- 范围裁决：只做 **A 层（部门流程预设）**。不实现 B 层「下单即流水线自动拆单派发」；不新增工具；不改动既有 13 个 company_* 工具的语义。

---

## 1. 目标与范围

1. 插件内置一个「游戏开发模式」预设（id `game-dev`）：7 阶段流水线（立项 → 原型 → 开发 → 美术 → 测试 → 验收 → 迭代），每阶段带：目标、负责角色、参与角色、交付物、验收门禁；另带 7 个岗位槽位定义（制作人/主策划/系统策划/客户端/服务端/美术 UI/测试）。
2. 部门可「套用」预设：`company.departments[i].preset = { id, version, appliedAt, appliedBy }` 持久化到 company.json；可切换、可清除。
3. 「查看」闭环：`company_status` / `GET /company/overview` 返回预设目录与部门已解析的预设（含岗位槽位 → 实际员工映射）；面板在总架构部门卡显示模式徽章，在部门架构弹层新增「开发模式」页签展示阶段流水线，并可套用/切换/清除。
4. 支持任意部门套用（不限于 D04），本次验收样本是现有游戏开发部 D04（dept-mviizjib-q10k，编号 D04）。

**不做**：自动拆单/派单、阶段状态推进、按预设强制岗位校验、跨部门模板复制。

### 3.3 岗位匹配算法（matchPresetRoles，必须确定性）

> v1.1（Lead 修订）：原「单一 haystack」会让弱字段（duties/skills）里的关键词把本属于后续槽位的员工抢走（如客户端职责写「配合策划」被 system-planner 抢走）。改为**强/弱字段分级**；对现有 D04 数据结果不变。
>
> v1.2（Lead 修订，独立审阅 P2 裁决）：`createDepartment` 的 `appliedBy` 固定 `"owner"`（不扩展签名）；`applyPresetToDepartment` 的快照 version 固定取注册表当前 version，显式 version 不写入快照。两条均与实现现状一致，属契约口径修正，非行为变更。

输入：preset、employees（**同一部门的员工数组**，含 manager；可传 company.employees 过滤后的子集）。

1. 每个员工算两个 haystack（均 `toLowerCase()`）：
   - `strong`：`[title, displayName]` 拼接（岗位身份字段）；
   - `weak`：`[duties.join(" "), skills.join(" ")]` 拼接（职责/技能字段）。
2. 每个槽位对每个未占用员工算匹配分：任一 token（小写）出现在 `strong` 里 → **2 分**；否则任一 token 出现在 `weak` 里 → **1 分**；否则 0 分（不候选）。
3. 按 `roles` 声明顺序逐个槽位分配；每个员工最多占一个槽位（先到先得，后续槽位不得复用）。
4. 槽位有多个候选时排序（全部为确定性比较）：分数高者优先；若槽位 `channel === "M"`，`role === "manager"` 再优先；再按等级高者优先（rank = 该员工 `channels` 中与槽位 channel 相同条目的 level 数字；无则取 `emp.level` 数字；解析失败 -1；数字大者优先）；再按 `code` 升序（无 code 最后）；再按数组原序。
5. 无候选 → `employee: null`（面板显示「未分配」）。

D04 期望映射（用真实数据必须命中）：制作人=E0022、主策划=E0016、系统策划=E0017、客户端=E0018、服务端=E0019、美术=E0020、测试=E0021，7/7 无未分配。

## 4. company-org.mjs 改动

- `createDepartment(company, { id, name, accepts, capacity, borrowPolicy, charter, code, preset })`：新增可选 `preset`（string id 或 `{id}`）。创建后若传了 preset，等价调用 `applyPresetToDepartment` 并写回（`appliedBy` 固定 `"owner"`：创建动作只有面板/owner 一个来源，函数不额外暴露该参数，见 v1.2 修订）。未知预设抛 `E_UNKNOWN_PRESET`。
- `updateDepartment(company, id, patch)`：`allowed` 增加 `"preset"`：
  - `patch.preset === undefined` → 不动；
  - `patch.preset === null || patch.preset === ""` → 清除（调用 clearPresetFromDepartment）；
  - 其余 → 套用/切换（validatePresetRef → applyPresetToDepartment，`appliedAt` 用 `new Date().toISOString()`，`appliedBy: "owner"`）。
- 不得改变现有字段行为；`preset` 不参与 `accepts/capacity/charter` 校验。


- 数据目录：`--data-dir` 优先；缺省 `process.env.DSH_HOME || ~/.dsh` + `/storages/member-manager`（与插件 defaultDataDir 一致）。
- 实现：`new CompanyStore(dataDir)` → `load()` → `withLock` 内匹配部门（id 或 code，大小写不敏感）→ `applyPresetToDepartment` 或 `clearPresetFromDepartment` → `saveCompany` → `appendAudit({type:"department.preset.applied"/"....cleared", departmentId, presetId, source:"cli"})`。
- `--dry-run` 只打印将要写入的 preset 对象，不落盘。`--json` 输出单行 JSON 结果 `{ok, departmentId, departmentCode, preset}`。
- 部门不存在 → 退出码 2，stderr `部门不存在: <input>`；预设未知 → 退出码 2，stderr `未知预设: <id>`。
- 脚本不改其他数据；不要求 agents 上下文。
