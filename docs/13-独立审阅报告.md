## 2. A 段：宿主契约独立证据核查

> 所有结论附文件:行号证据，可直接 grep 复核。

### 2.1 followup 唤醒语义——跨邻接唤醒**成立** ✅（规格§1 关键假设验证通过）

- 证据：`dsh-agent-loop/lib/index.js:806-814` —— `followup(input)` 直接调 `this.send(input, "next-turn", true)` → `inbox.splice("next-turn", ...)` → `wakeDriver()`；**代码路径里没有邻接/parent 校验**。
- `ctx.agents.get(id)`（`dsh-agent/lib/index.js:596-598`）从全局 store 取任意 live agent，不限于自己创建的孩子。
- **邻接限制仅存在于**：
  - subagent 内建 `send_message` 工具（`dsh-subagent/README.zh.md:206-213` 所述"仅允许相邻模型消息"是该工具自己的约束，不是 Agent API 的约束）；
  - `subagents.prompt()`（UI→子会话的 browser 通道），要求 parent 在线。
- **结论**：规格 v2 §0 修正项"followup 公共 API 可唤醒任意活 Agent，不受父子邻接限制"**与源码一致**，架构决策 D1+followup 路线成立。wakeAgent 流程（get→resume→followup）正确。

### 2.2 agents.resume / agents.create 参数形态 ⚠️ 实现时必须对齐

- `ctx.agents.create(options)` 委托 factory 的 `createAgent(ownerCtx, options)`（`dsh-agent-loop/lib/index.js:1893`），关键字段：
  - `sessionId`（必填，uuid 字符串）
  - `agentOptions?: { provider, model, reasoningEffort, maxTokens }`
  - `setup?: (agentCtx, agent) => Promise<{commit}?>`——**这是安装 tools.restrict/systemPrompt 段/监听器的唯一窗口**（必须在 setup 内完成，announce 之前）
  - `parentAgent?`——不传 = root-level 根会话；传 = 运行时子级
  - `seed?, meta?, inheritedEventCount?, signal?`
- `ctx.agents.resume(options)` 委托 factory 的 `resume(ownerCtx, options)`（`dsh-agent-loop/lib/index.js:1963-2019`），关键字段：
  - **`resumeSessionId`**（不是 `sessionId`！）
  - 同样接受 `agentOptions/setup/parentAgent/signal`
  - 恢复时会自动 append 中断回合闭合器（`interruptedTurnClosers`，L1992），不需要运行时自己收尾
  - **前置条件**：必须有 `sessionPersistence` backend 注册，否则抛 `"cannot resume: session persistence is not configured (load a dsh-session-persistence backend)"`（L1965）——DSH 桌面/CLI 默认已装，但若插件在没有 persistence 的环境（测试 mock）下启动要做降级处理。
- **契约 docs/11 §wakeAgent** 写的是 `agents.resume({ resumeSessionId: id })`——**与源码一致**，✅。

### 2.3 🔴【阻断 B1】tools.restrict 的作用域陷阱——三线隔离**单靠 restrict 不够**

- 证据：`dsh-tools/lib/index.js:2991-3005`（restrict 实现）+ L3040-3043（restriction 语义注释）：
  > "A restriction filters what a scope inherits — the global layer and every ancestor layer on its chain — and **never what its OWN layer registers**."
- 关键点：
  1. `tools.restrict(filter)` 必须在 `agent.ctx` 作用域下调用（L2993），全局 ctx 调用直接抛错。
  2. `filter` 形态严格是 `{ allow?: string[], deny?: string[] }`，两者至少一个；元素必须是**全局注册的工具名**（`restrictableNames`，L3002-3004），命名未知工具会抛错。
  3. **不能命名 `"run_code"`**（L3001，PTC 保留），员工/经理线要拒 run_code 得通过 sandbox/guard 而非 restrict。
  4. **最致命**：restrict **只过滤"继承来的全局工具"**，不拦截目标 agent 自己在 `agent.ctx.tools.define()` 注册的工具（即"scope-local registrations remain visible"，L2987）。
- **对公司化改造的含义**：如果在 setup 里先 `childCtx.tools.define('company_assign', ...)` 再 `childCtx.tools.restrict({deny:['company_assign']})`——**restrict 拦不住**，因为 company_assign 是 child 自己层注册的，不属于"inherited"。
- **正确做法**（三选一，推荐前两组合用）：
  - **(a)** 把 company_* 工具全部注册在**全局层**（插件根 ctx），然后每个 agent 在 setup 里用 `agent.ctx.tools.restrict({ allow: [...该线允许名单...] })` 做交集白名单——这是 restrict 唯一可靠的用法。
  - **(b)** 第二道防线用 `agent.ctx.tools.guard(exec => ...)` 在 pre-execute 阶段反查 `exec.agent` 归属，越权返 `E_TOOL_LINE`——这正是契约 docs/11 §工具行隔离 提到的"双保险"里的第二道。(a)+(b) 双保险是必要的，不是可选。
  - (c) 在 setup 时**只注册该员工/经理该看到的工具**（懒注册），不做全局 company_* 全集——这在员工数量大时（>50）有 setup 开销，但语义最直观；缺点是临时动态加线困难。
- **最小修复建议**：在运行时 setup 回调里采用 (a)+(b)：全局注册 13 个 company_* 工具 + 每条线 setup 调 `restrict({allow: [...]})` + 注册 `tools.guard` 反查 agent→line 映射兜底；工具名不在 allow 里自动屏蔽；guard 做运行时二次校验防竞态。
- **若 plugin-builder 按"在 agent.ctx 上 deny 自己定义的工具"写，三线隔离彻底失效——员工能调到 company_assign，经理能调到 company_order——这是 P2 闭环跑通前必须对齐的阻断项。**

### 2.4 🔴【阻断 B2】drainChildren 的"直接子级"硬约束——部门根会话释放路径需重新设计

- 证据：`dsh-subagent/lib/index.js:1372-1383`：
  ```js
  async drainChildren(parent, childIds) {
    if (this.ctx.agents.get(parent.id) !== parent) throw UNAUTHORIZED;
    for (const childId of childIds) {
      const activation = this.resident.get(childId);
      if (activation.parent.id !== parent.id || !activation.ancestry.has(parent))
        throw UNAUTHORIZED("not a direct child");
    }
    // dispose + disposeRoots
  }
  ```
- 关键点：
  1. `parent` 必须是**确切的 live Agent 实例**（不是 id 字符串），且必须是每个 child 的**直接 parent**；
  2. **不递归**——要释放孙辈/非直接孩子，必须逐层调用或走 `drainDescendants(parents)`（L3118-3122）。
- **对公司化改造的含义**：
  - 部门根会话在 boot 里用 `agents.create({sessionId: deptRootId})`（无 parentAgent）是 root 级，不是 runtime Agent 的孩子；
  - 员工若由"部门经理会话"通过 setup 里的 subagents.startActivation 创建，那员工的 parent 是**经理 Agent**，不是公司 runtime；
  - Shutdown 时直接调 `subagents.drainChildren(runtimeAgent, [...allEmployees])` **会 100% 抛 UNAUTHORIZED**——因为员工不是 runtimeAgent 的 direct child。
- **正确做法**（两选一或组合）：
  - **(a)** 所有员工/临时工统一由 runtime Agent（插件根 ctx 的 owner）调用 `subagents.startActivation({ request: { parent: runtimeAgent, ... }})` 创建，部门经理通过 followup 指挥而非作为 subagent parent——结构扁平，drainChildren 一键释放；缺点是 listChildren 只能按 runtime 列，需要自己账本维护部门→员工映射。
  - **(b)** 保留经理→员工的 parent 关系（便于 listChildren 按部门查看），shutdown 时递归：对每个部门经理先 `managerAgent.cancel(keepInbox:true)` + `whenIdle`，再调用 `subagents.drainChildren(managerAgent, [...deptEmployees])`，最后 `handle.dispose()` 经理；部门根会话因为是 root 级，不走 drainChildren，直接 `handle.dispose()`。
- **契约 docs/11 提到 shutdown 顺序是"停派工→whenIdle→cancel(keepInbox)→drainChildren→写审计"**，但没有指定 parent 是谁——实现时必须按上述 (a) 或 (b) 明确所有权模型，否则 shutdown 阶段 UNAUTHORIZED 会抛到最外层，dispose 路径卡住导致进程退不干净。

### 2.5 ⚠️【重要 I1】UserMessage.source 是开放结构，不需要 harness-compat 版本分支

- 证据：`dsh-llm/lib/types/message.js:53-58`（createUserMessage 不校验 source 字段）+ `dsh-agent/README.zh.md:50-57`（示例用 `{kind:'user'}` 和 `{kind:'my-plugin'}`）+ dsh-subagent 内部使用 `{kind:'agent-message',form:'relay',senderSessionId}` / `{kind:'subagent-settled',...}`。
- **结论**：本宿主 source.kind 不是枚举，plugin 自定义消息直接用 `{ kind: 'company-runtime', ... }` 即可，**不需要从 dsh-agent-teams 搬 `harness-compat.js` 做 session/clone 版本探测**（那个是 A 面对旧宿主的兼容层，本宿主没有 source.kind 白名单）。
- 若 plugin-builder 把 harness-compat.js 整块搬过来，属于冗余代码（非阻断，但增加维护成本与错误面）。建议只保留必要的"符号探测"（如 startActivation 是否存在），source 部分直接写死 `{kind:'company-runtime'}`。

### 2.6 ⚠️【重要 I2】assistant/message.usage 字段直接来自 provider adapter，结构**未规范化**

- 证据：`dsh-agent-loop/lib/index.js:1110,1160`——`...live.usage === void 0 ? {} : { usage: live.usage }` 原样透传；`dsh-llm/lib/types/assembler.js:73-74,166-168`——`this._usage = chunk.usage`，不做字段映射。
- **结论**：规格 §16.2 V7 要求"按 attempt/员工/部门/项目四维累加"，但 usage 字段名（是 `inputTokens`/`outputTokens` 还是 `prompt_tokens`/`completion_tokens`、有没有 `cacheReadTokens` 等）依 provider adapter 而定。运行时必须：
  - 做 provider→字段名的适配表（或通过 `usage.promptTokens??usage.input_tokens??usage.inputTokens` 这样的兜底链）；
  - 处理 usage 为 undefined 的情况（某些 stream 不发 usage chunk）；
  - 缓存读 token 单独计。
- 不要假设 `usage.inputTokens` 固定存在；否则成本统计要么全 0，要么抛 TypeError。

### 2.7 ⚠️【重要 I3】whenIdle 在异常/卡死时可能永远不 resolve——shutdown 必须加超时

- 证据：`dsh-agent-loop/lib/index.js:870-875`——`whenIdle()` 是循环 `await activityDone`，没有内置超时。如果 driver 因为未捕获异常卡住或 activityDone 链断裂，await 会挂住。
- **契约建议**：docs/11 的 shutdown 序列里"等 whenIdle"必须包装成 `Promise.race([agent.whenIdle(), timeout(ms)])`，超时进入强制 cancel+drain 分支，否则插件卸载会卡死宿主。

### 2.8 ⚠️【重要 I4】inject 必须扩为 6 项，但 storage 不必走 ctx.storage

- 证据：现有 `lib/index.js:47`——`inject = ["tools", "webServer"]`；规格 §11 M1 + 契约 docs/11 要求扩为 `["tools","webServer","agents","subagents","llm","systemPrompt"]`——必须改。
- 关于 storage：现有 `defaultDataDir()`（L82-85）直接用 fs 写 `~/.dsh/storages/member-manager/`，不经过 `ctx.storage` backend——这符合规格 §16.2 V4"放插件全局 storage，不放 workspace"的要求。不强制切到 `dsh-storage-json`，但建议账本写盘用原子写（`dsh-storage-json` 的 writeAtomic 模式：写 tmp→fsync→rename→fsync dir；Windows 下跳过 dir fsync）；否则 crash 时可能写半截 JSON。
- ctx.storage 如果 inject 进来，可用于未来迁移到 sqlite backend，不是 P1 必需。

### 2.10 startActivation 关键参数与错误码（备查）

- 签名（综合 `dsh-subagent/lib/index.js` 与 README）：`subagents.startActivation({ provider, label, request: { prompt, parent, cwd?, agentOptions?, agentPreset?, maxDepth?, outputSchema? }, delivery: 'parent'/'caller', signal })`
- 返回 `{ childId, messageId?, result, dispose }`：
  - `delivery:'parent'`：常驻 continuable 子会话，result 在整个后代树都结算后才 resolve（适合 resident 员工/部门经理）；
  - `delivery:'caller'`：一次性，result settle 后自动 dispose（适合 per_task 临时工）；
- 关键错误码（抛 SubagentError，code 字段）：`ACTIVATION_LIMIT_REACHED`（容量耗尽，不排队）、`NOT_RESUMABLE`、`DRAINING`、`ACTIVATION_CLOSING`、`UNAUTHORIZED`、`DUPLICATE_CHILD`、`CANCELLED`——运行时 catch 时必须按 code 分流处理（容量耗尽→排队/借调；NOT_RESUMABLE→新建；DRAINING→等 shutdown 完成后拒绝新单）。

### 2.11 cancel(keepInbox) 语义（对齐契约）

- 证据：`dsh-agent-loop/lib/index.js:815-821`：`keepInbox:false`（默认）= 中止轮次**并清空** next-turn/next-step 收件箱；`keepInbox:true` = 仅 abort 当前活动，收件箱保留。
- shutdown 用 `cancel(cause, { keepInbox:true })` 正确；但要注意 keepInbox 后待处理消息会在下次 wakeDriver 时被消耗——dispose 路径需要确保不再 wake。
- 用户主动 stop 走 `cancel({kind:'user'})`（keepInbox 默认 false），与 `workspace/session-stop` 处理一致（dsh-agent/lib/index.js:33-35）。

**B1 / B17 🔴 阻断 — guard 返回空字符串 = 拒绝所有工具（合并说）**
